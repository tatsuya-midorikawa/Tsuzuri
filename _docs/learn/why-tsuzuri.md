# なぜ Tsuzuri か

[ドキュメントのトップ](../README.md) | [概要](overview.md) | [コードサンプル](code-samples.md)

Tsuzuri は、**関数型の式で計算を組み立て、所有権で値の寿命を検査し、その計算を native と WASM のホストへ組み込めるようにすること**を目指しています。処理を簡潔に表現することと、値の受け渡しや実行の仕組みを把握できることを両立させるための言語です。

このページでは、その設計を選ぶ理由、C/C++・Rust・C#/F# と比べた長所と制約、どのような処理に活用できるかを紹介します。対象は Tsuzuri 0.1.0 の現在の実装です。

## 目指したところ

設計上の目標は、**C/C++ を上回る性能と、C#/F# 以上の書きやすさを両立すること**です。高水準の記法を使うために実行時の負担を受け入れるのでも、性能のために安全性や読みやすさを諦めるのでもなく、その両方を処理系の課題として扱います。

そのために、Rust にも見られる所有権と借用を採用しつつ、関数の合成、パターンマッチ、計算式を言語の基本にしています。値の型と寿命をコンパイル時に検査し、具体型への特殊化や不要なコピーの除去を通して、機械語へ近づけます。

ただし、これは目標であって、現時点で達成済みという宣言ではありません。性能は対象処理と環境をそろえて測定し、書きやすさは記述量だけでなく、読み解く負担、所有権の扱い、ライブラリ、デバッグまで含めて評価します。以下の優位点も、用途に合う場合の利点として読んでください。

## 関数型の書き方を計算部分に使いたい

値を渡し、関数を組み合わせ、データの形で分岐する書き方を基本にしています。カリー化、部分適用、パイプ、レコード、union、パターンマッチを使いながら、LLVM による native / WASM 出力を選べます。

```tsuzuri run=42
def add :: Add<'value> -> 'value -> 'value = \left right -> left + right

let add_twenty = add 20i64
22i64 |> add_twenty
```

`Add<'value>` は、その型が加算を提供するという制約です。この例では `i64` の加算として具体化されます。関数を組み合わせる記法と、実行時に型を調べて操作を選ぶ仕組みは同じものではありません。

データの形はレコードと union で表し、その処理を小さい関数へ分けられます。検証、変換、集計の流れを、値がどこからどこへ渡るかに沿って読むことができます。詳しくは[関数](../language-reference/functions.md)と[型クラス](../language-reference/generics-and-typeclasses.md)を参照してください。

## 値の受け渡しを API の契約にしたい

読み取る関数には `ref T`、排他的に扱う関数には `ref mut T`、所有権を受け取る関数には `T` を使います。型を読むことで、その関数へ値を貸すのか、所有値として渡すのかを区別できます。

借用中の所有者の移動や、非 Copy 値の移動後の再使用はコンパイル時に検査します。所有値の解放はコンパイラが生成するため、通常の Tsuzuri コードで手動の解放処理を組み立てる必要はありません。

これはメモリのコストが消えるという意味ではありません。コレクションの独立コピー、捕捉環境の複製、フレーム外への値の移送は、確保やコピーを伴うことがあります。GC の停止がないことだけを根拠に、ハードリアルタイム性を保証することもできません。

例えば配列の更新 API は、所有値を受け取って更新後の値を返します。元の Copy 配列も後で使う場合は独立したコピーを保ち、一意な所有ヒープバッファなら再利用できます。値の意味と更新のコストを合わせて考えるための規則です。[所有権](../language-reference/ownership.md)と[配列の API](../library-reference/arrays-and-lists.md)に詳しい契約があります。

## 失敗と数値の意味を明確にしたい

回復可能な失敗は `Option` / `Result` で返し、`match` や `let!` で処理します。理由のない値なしと、理由付きの失敗を型で区別できます。一般の例外を `try` / `catch` で捕捉するモデルではありません。

数値も、最適化の都合で意味を変更しないことを重視しています。

- 通常の整数加減乗算は型の幅で折り返します。検出付き・飽和演算は `Int` の別 API です。
- 整数のゼロ除算や範囲外アクセスなどはトラップです。`Result` に自動変換されません。
- 浮動小数点の丸め、NaN、符号付きゼロを保ちます。通常の式を勝手に fast-math として扱いません。
- `-O3` は安全検査を外してよいという指定ではありません。

値として失敗を表せることと、プログラムが必ず成功・停止することは別です。非停止やスタック枯渇は起こり得ます。詳しくは[数値](../language-reference/numbers.md)と [Option / Result](../library-reference/option-result.md)を参照してください。

## 既存アプリケーションに計算を組み込みたい

Tsuzuri が担当するのは、データ変換、判定、集計、数値計算などの部分です。画面、DOM、ネットワーク、デバイスとの接続はホストに残し、`export def` / `extern def` で境界を定義できます。ファイル、ディレクトリ、環境、時刻、乱数、プロセスは標準の [OS API](../library-reference/os.md) でも扱えますが、既定の WASM 出力では使えません（`E2000`）。`--wasm-host wasi` を指定すると WASI preview1 の import として接続できます。

例えば、ブラウザーの画面とイベント処理は JavaScript に、入力から結果を求める処理は WASM にできます。native では、C ABI を介して既存のホストから呼び出せます。小さい計算部分だけを別言語にする構成を試せます。

ただし、境界には引数変換、バッファの確保・移送、呼び出しなどのコストがあります。細かすぎる呼び出しや頻繁な文字列変換は、計算部分の最適化より高くつく場合があります。処理を一括で渡せるか、結果回収まで含めて測る必要があります。

また、ホストは ABI と所有権を守る責任を持ちます。任意の C ポインターの正しさや、ホスト側の共有状態まで Tsuzuri の借用検査が保証するわけではありません。[C 連携](../guides/native-interop.md)と [WASM 連携](../guides/webassembly.md)で境界の契約を確認してください。

## 人とツールが同じ契約を確認したい

関数の型を明示し、暗黙の数値変換を避け、型・所有権・網羅性の問題をコード生成前に検査します。`--json` による位置付き診断は、エディターや自動化からも利用できます。

`test` 宣言、保守的な formatter、言語サーバー、API 文書生成を同じコンパイラに備えています。AI が生成したコードも人が書いたコードも、同じ検査と実行結果で確認できます。これは生成コードの正しさを保証するものではなく、検証の入口を共通にする設計です。

エディター機能には未対応範囲もあります。例えば現在の LSP は補完や rename を提供しません。詳しくは[開発ツール](../tools/README.md)と [VS Code 拡張機能](../../vsc/README.md)を参照してください。

## 性能と移植性を一緒に考えたい

連続した配列、具体型への特殊化、所有権に基づく不要なコピーの除去によって、最適化しやすいコードを生成します。LLVM の自動ベクトル化に加え、明示的な SIMD 型や CPU 並列処理も利用できます。

並列化したい計算は `Task.parallel` や `Parallel` で指定します。native ではワーカープールを利用し、WASM の既定経路では逐次実行します。WASM threads を有効にする場合は、共有メモリと Worker ホストを明示的に用意します。処理の表現と、実行環境の要求を分けて扱えます。

速さはバックエンドの名前だけでは判断しません。小さい入力では逐次処理の方が有利なこともあります。正しい結果までに必要な確保、起動、転送、同期を含めて測り、使う環境に合った経路を選ぶことを重視します。

## C/C++ と比べると

C/C++ は、既存の native 資産、低水準の制御、成熟した最適化基盤を持ちます。Tsuzuri はその性能を目標としながら、計算の実装で利用者が手作業で守る契約を減らそうとしています。

### C/C++ に対する優位点

- 所有権と借用の規則を言語として検査し、移動後の再使用や借用の競合をコード生成前に拒否します。C++ の RAII やスマートポインターも資源管理に役立ちますが、通常の C/C++ の言語仕様だけで、すべての参照の寿命が同様に検査されるわけではありません。
- `union` と網羅的な `match`、`Option` / `Result` を基本の書き方として使えます。C++ にも対応するライブラリ機能はありますが、Tsuzuri では値の状態とその処理を同じ言語規則で表せます。
- C/C++ の符号付き整数オーバーフローが未定義動作になるのに対し、Tsuzuri の通常の整数加減乗算は型の幅で折り返します。最適化レベルを変えてもこの規則は変わらず、検出や飽和が必要なら別 API を選べます。

### C/C++ に対する劣位点

- ポインター、メモリ配置、allocator、任意の外部 ABI を細かく制御する自由度は小さく、デバイス、ネットワーク、既存ライブラリとの接続にはホスト実装が必要です。ファイル、環境、時刻、乱数、プロセスは標準の OS API で扱えますが、対象は Windows を除く native と `--wasm-host wasi` で、Windows の native では使えません。既存の C/C++ コードをそのまま取り込めるわけではありません。
- 対応プラットフォーム、最適化済みライブラリ、デバッガー、長期運用の実績は C/C++ の方が豊富です。Tsuzuri の GPU は実験段階であり、成熟した GPU 向け開発基盤の代替にはまだなりません。
- 安全検査、所有値の複製、ホスト境界の変換にはコストがあります。C/C++ 側でも同じ計算を効率的に実装できるため、LLVM を使うことや所有権を持つことだけで速度優位は決まりません。

既存の C/C++ ホストを維持し、入力と結果が明確な計算部分へ型・所有権の検査を導入したい場合に、Tsuzuri を切り出して試せます。

## Rust と比べると

GC に依存しないメモリ管理、所有権と借用、native / WASM 出力は Rust とも共通する方向性です。これらを備えること自体は、Rust に対する Tsuzuri 独自の優位点ではありません。主な違いは、処理をどう記述するかと、どこまでの自由度を提供するかです。

### Rust に対する優位点

- カリー化、部分適用、パイプを基本の関数適用として使えます。関数を渡して変換・集計をつなぐ処理では、その流れに沿った記述を組み立てやすくなります。Rust でもクロージャーや iterator で表現できますが、Tsuzuri はこの書き方を言語の中心に置いています。
- `Option` / `Result` / `IO` や独自ビルダーを、共通する `let!` / `return` の記法で合成できます。失敗や入出力を含む計算の流れを同じ形で読みたい場合の利点です。

### Rust に対する劣位点

- 借用で表せるデータ構造に制限があります。可変スライス、排他借用フィールド、レコード内の独立した複数の region は未対応で、Rust なら表現できる構造でも設計を変える必要があります。
- Copy のコストモデルが異なります。Rust の `Copy` はビット単位の複製ですが、Tsuzuri の Copy 配列や捕捉を持つ関数値の複製は、ヒープ確保や所有データの深いコピーを伴う場合があります。記述が短くても、費用が小さいとは限りません。
- Cargo、crates.io、非同期 I/O、低水準 API、開発ツールの成熟度と選択肢では Rust に及びません。Tsuzuri のパッケージは現在ローカル path 依存に限られ、`Task` も非同期 I/O の executor ではありません。

関数の合成を中心に書きたい計算には Tsuzuri の記法が合う可能性があります。一方、所有権を使う汎用アプリケーションを豊富なライブラリとともに構築するなら、現在の Rust の方が選べる構成は広くなります。

## C#/F# と比べると

C#/F# は、静的な型検査と .NET のライブラリを組み合わせてアプリケーションを構築できます。特に F# には、カリー化、パイプ、判別共用体、コンピュテーション式がすでにあります。Tsuzuri が目指すのは、そうした表現のしやすさと、GC に依存しない実行モデルの両立です。

### C#/F# に対する優位点

- 所有権に基づいて値を解放するため、GC による回収のタイミングを性能設計に織り込む必要がありません。短い計算を繰り返す用途や、メモリの寿命を API で明確にしたい用途で利点になります。ただし、確保・解放のコストや遅延までなくなるわけではありません。
- .NET ランタイムを前提にせず、計算を native / WASM のモジュールとしてホストへ組み込めます。入出力を使わない既定の WASM はランタイムの import を必要とせず、計算部分の依存関係を小さく保てます。出力サイズや起動時間の優位は別途測定が必要です。

### C#/F# に対する劣位点

- .NET の標準ライブラリ、NuGet、GUI、Web、データベース、ネットワーク API をそのまま利用できません。標準の OS API はファイル、ディレクトリ、環境、時刻、乱数、プロセスに限られ、JSON と正規表現の標準ライブラリもありません。入出力中心のアプリケーションでは、ホスト側の実装量が増える場合があります。
- 文字列補間（`$"..."`）と書式指定は使えますが、幅は Unicode scalar の数で数えます。書記素の幅、locale、桁区切りには対応していません。
- GC に任せられる共有データや循環構造も、Tsuzuri では所有権に沿って設計する必要があります。借用、移動、明示的な複製を学ぶ負担があり、あらゆる処理で C#/F# より簡単になるわけではありません。
- C# の `async` / `await` や F# の非同期ワークフローに相当する汎用的な非同期 I/O 基盤はありません。対話環境や IDE 支援も発展途上です。画面や通信を含む開発体験では、成熟した .NET の環境が有利です。

C# にも .NET Native AOT があるため、native 出力だけを固有の優位点とはしません。違いは、所有権によるメモリ管理と、ホストへ組み込む計算を中心に設計していることです。F# に慣れた利用者は、記法の共通点だけでなく[移行時の意味の違い](../guides/from-fsharp.md)も確認してください。

## 採用前に小さく確かめる

最初からアプリケーション全体を移すのではなく、入出力と期待値が明確な計算を一つ選ぶと判断しやすくなります。

1. [コードサンプル](code-samples.md)と[入門](../get-started.md)で、対象環境のビルド・実行・テストを確認する。
2. 必要な型、ライブラリ、ABI、失敗の扱いが[現在の対応範囲](../feature-status.md)にあるか確認する。
3. 空入力、境界値、失敗入力を含めて、既存実装と結果を照合する。
4. 確保・変換・転送・同期を含む同じ仕事を測定し、保守と配布の手順も比較する。

特に、標準のネットワーク API、JSON や正規表現、registry / git 依存、汎用的な GPU 実行を前提にしないでください。標準の OS API は Windows の native では使えません。GPU は実験段階で、Windows 上の実行検証も未完了です。必要なライブラリや対象環境がそろうかまで含めて、利用する範囲を決めます。

測定条件と制限は[性能ガイド](../guides/performance.md)と[ベンチマーク](../../docs/benchmarks.md)にまとめています。
