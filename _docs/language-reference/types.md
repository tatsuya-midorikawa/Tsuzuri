# 型と型推論

[ドキュメントのトップ](../README.md)

Tsuzuri は静的型付きの言語です。関数の境界とレコードのフィールド型を明示し、ローカルな式は文脈から推論します。型が合わない値を暗黙に変換したり、実行時の動的型へ置き換えたりしません。

## 基本型

| 型 | 意味 |
| --- | --- |
| `bool` | `true` または `false` |
| `unit` | 値は `()`。意味のある結果を返さない操作に使う |
| `i8`, `i16`, `i32`, `i64`, `i128` | 符号付き整数 |
| `i8u`, `i16u`, `i32u`, `i64u`, `i128u` | 符号なし整数 |
| `byte`, `ubyte` | `i8u` の別名 |
| `sbyte` | `i8` の別名 |
| `bigint` | 任意精度の整数（std の `BigInt`） |
| `f16`, `f32`, `f64`, `f128` | IEEE 754 の binary 浮動小数点 |
| `d32`, `d64`, `d128` | IEEE 754 の decimal 浮動小数点、BID 表現 |
| `char`, `utf8char` | UTF-16 コード単位、Unicode スカラー |
| `string`, `utf8string` | UTF-16 コード単位列、妥当な UTF-8 バイト列 |

`Int` / `Float` / `Bool` / `Unit` はこれらの型名の別表記ではありません。`Integer` や `Float` は型クラス制約の名前として登場しますが、具体的な数値型とは区別します。

## 型の組み立て

| 表記 | 意味 |
| --- | --- |
| `i64 * string` | 二要素タプル |
| `[i64]` | 長さを型に含めない配列 |
| `[f64; 3]` | 長さを型に含める固定長配列。要素を値の中に直接持つ |
| `[\|i64\|]` | 不変の単方向連結リスト |
| `Pair<i64, string>` | ジェネリックなレコードなどの具体化 |
| `Maybe<i64>` | 値がない場合を含む union |
| `Result<i64, string>` | 成功値または失敗値を持つ union |
| `Vec<i64>` | 伸縮可能な所有バッファ |
| `Map<i64, string>`, `Set<i64>` | 順序付きコレクション |
| `Seq<i64>` | 一回消費する反復状態 |
| `i64 -> i64` | 一引数の関数値 |
| `Task<i64>` | 一回実行の遅延計算 |
| `ref T`, `ref mut T` | 共有借用、排他借用 |
| `i32x4`, `f32x4` など | 128-bit SIMD ベクトル |

型名と型引数の `<` は隣接させ、型引数はカンマで区切ります。`Pair i64 string` や空の `Pair<>` は使えません。

## タプル

```tsuzuri run=42
def first :: i64 * bool -> i64 = \pair ->
    match pair with
    | (number, _) -> number

first (42, true)
```

タプルの値は `(value, other)`、型は `Type * OtherType` です。各要素は別の型を持てます。取り出しにはパターンを使い、`pair.0` のような数値メンバーアクセスは使いません。

タプルは要素ごとに所有権を持ち、全要素が Copy ならタプル全体も Copy になります。関数の複数引数とタプル一引数は別物です。

## 固定長配列

```tsuzuri run=32
def dot :: [f64; 3] -> [f64; 3] -> f64 = \a b -> a[0] * b[0] + a[1] * b[1] + a[2] * b[2]

let a: [f64; 3] = [1.0, 2.0, 3.0]
let b: [f64; 3] = [4.0, 5.0, 6.0]
let d = dot a b
d as i64
```

`[T; N]` は長さ N を型に含む配列で、要素をタプルと同じく値の中に直接持ちます。ヒープを確保せず、要素が Copy なら配列全体も Copy で、複製は値のコピーだけです。N は接尾辞のない 0 から 1024 までの整数で、`[T; N]` と `[T; M]`、`[T]` はそれぞれ別の型です。

配列リテラルは、固定長配列が期待される位置でだけ固定長配列になり、要素数が N と違えば `E1003` です。添字、`.length`、共有スライス、`ref [T]` の引数への受け渡しが使えます。範囲外の添字は実行時にトラップし、範囲内の整数リテラルの添字だけは検査を省きます。要素の代入、パターンによる分解、`for` による列挙、`==` などの構造的なインスタンスはありません。生成と利用は [固定長配列の API](../library-reference/arrays-and-lists.md#固定長配列) を参照してください。

### 長さパラメーター

```tsuzuri run=10006
const SIZE: i64 = 3

record Grid<'a, const N: i64> { cells: ['a; N] }

def total :: [i64; N] -> i64 = \values ->
    let mut sum = 0i64
    for index in 0i64 .. (values.length - 1) do sum = sum + values[index]
    sum

let grid = Grid { cells: [1, 2, 3, 4] }
let row: [i64; SIZE] = [1, 2, 3]
total grid.cells * 1000 + total row
```

レコード・union・型別名は `const N: i64` を型パラメーターに書き、長さを受け取れます（`Grid<f64, 3>`）。関数のシグネチャの `[T; N]` の N は、型変数 `'a` と同じく呼び出しごとに推論される長さパラメーターです。ただし同じ名前の `i64` 定数があれば、その値を長さとして使います。長さに使える定数は、型が `i64` で値が整数リテラルの `const` だけです。長さの算術（`N * 2`）や、本体での N の値としての使用はできないので、長さは `.length` で読みます。具体化した長さごとに関数は別に特殊化されます。

## 推論と明示的な変換

```tsuzuri run=42
let narrow: i32 = 40
let wide = narrow as i64
wide + 2
```

接尾辞のない整数リテラルの型は、型注釈・引数型・演算相手に加えて、Rust と同じく後の使用からも推論します。`let values = [3, 5, 8]` は、後で `[i64]` を受け取る関数へ渡せば `[i64]` です。何も型を決めなければ `i32` です。浮動小数点が期待される位置の整数リテラルは浮動小数点の値です。小数点または指数を持つリテラルは既定で `f64` です。いったん型が決まった通常の数値束縛を、後の使用に合わせて別の幅へ変えることはできません（[数値](numbers.md#リテラルと型)）。

`i32` の変数と `i64` の変数、整数と浮動小数点は暗黙に混合できません。`as` などの明示変換を使います。`let value: T = expression` は型注釈であり、値の変換ではありません。

## 多相性の境界

名前付き関数のシグネチャの `'a` は呼び出しごとに具体化されます。同じ型変数は同じ型、異なる変数は独立した型です。

```tsuzuri run=42
def identity :: 'a -> 'a = \value -> value

let amount = identity 42
let text = identity "ready"
assert (text.length == 5)
amount
```

ローカルな関数値は単相です。型変数が解決できない値や、高ランク多相を必要とする使い方は拒否されます。型クラスは使える操作を制約し、インスタンスの選択はコンパイル時に完了します。

## レイアウトと上限

値の保守的なレイアウトは 64 KiB が上限です。配列や文字列のバッファ本体、リストのノード、クロージャーの捕捉環境は、この値レイアウトとは別の記憶域です。そのため、64 KiB はすべての配列データの合計サイズ上限ではありません。

固定長配列は要素を値の中に持つので、その大きさは N × 要素の大きさとしてこの上限に数えます。`[[i64; 1024]; 8]` はちょうど 64 KiB で受理し、`[[i64; 1024]; 9]` は `E1010` です。大きな値を多くの局所変数に置くと、特に WASM でスタックを使い切ることがあるので、大きな作業領域には `[T]` を使います。

型の展開・具体化には深さや構成要素数の制限があります。上限に達した場合はコンパイル時に診断し、不完全な型のままコードを生成しません。
