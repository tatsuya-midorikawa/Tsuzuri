# Misused `Domain.run`

## What it covers
`Domain.run body` calls `body ()` in a failure domain: a trap inside becomes `Result.Error`, what the call allocated is freed, and the program goes on. That is safe only for a computation that leaves nothing half updated, so each call is checked in this order, and the first broken rule is reported: `Domain.run` is called directly with one argument; the argument is a lambda or the name of a `pure def`; the lambda captures plain data only (no function, `dyn`, task, `Rc`, `Arc`, extern handle, or user `Drop`); its body, and what it calls, is pure (no I/O, debug output, clock, task, shared state, GPU, `extern`, or nested `Domain.run`); its result is plain data. A build that cannot hold a domain is reported too: WebAssembly, `--freestanding`, a non-system allocator, native Windows, `--emit llvm` without `--trap-mode return`.

## Fixes
- Write the computation as a lambda at the call: `Domain.run (\() -> ...)`.
- Compute a captured function or handle inside the closure, or capture the plain data it needs.
- Move the I/O or other effect out of the closure, before or after the call.
- Return plain data from the closure.
- Build for native macOS or Linux with the system allocator, or add `--trap-mode return` to `--emit llvm`.
