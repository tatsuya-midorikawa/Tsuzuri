## 目的

一つの関数の中にある独立した複数のエラーを一度に報告し、壊れた式の周辺でも型情報を得られるようにする。
LSP の補完（G12）と REPL（G13）の前提になる。

## 現状

- 「関数内の最初の型／所有権エラーからの完全な回復は行いません」「字句エラーがあるファイルは構文検査へ、構文エラーがあるプロジェクトは型検査へ進めません」（docs/language.md 診断）。
- 「関数のシグネチャが壊れている場合は、その関数の使用による二次エラーを抑制し、他の関数を検査します」。
- 構文エラーは括弧の外側・行頭の宣言境界で回復する（`src/parser.rs`）。診断は重複を除いて 1000 件まで収集し、50 件まで表示する（`src/diagnostic.rs`）。

## 仕様

### Phase 1: 型検査の式単位の回復（実装対象）

- 型エラーになった式に内部の `Type::Error` を与え、同じ関数の後続の文・式の検査を続ける。`Type::Error` は単一化で任意の型と一致し、それに起因する二次エラーを報告しない。
- `Type::Error` を含む関数は所有権検査・単相化・コード生成へ進めない。エラーが一つでもあれば従来どおり `build`／`run` は LLVM へ進まない（型付き IR の不変条件は型検査で保証し、`Type::Error` が LLVM へ到達しないことを GUIDE §1.9 に従って構造的に保証する）。
- 報告順は既存の安定順（ソース ID・位置・コード・メッセージ）。

### Phase 2: 構文の文単位の回復（設計方針）

- ブロック内の文の境界（`;`、改行、インデント）で回復し、壊れた文を `ExprKind::Error` に置き換える。LSP と `check` だけがその AST を後段へ渡す。

### Phase 3: 所有権検査の回復（設計方針）

- 最初の `E1012`／`E1013`／`E1014` の後も、別の値に関する検査を続ける。同じ値に起因する連鎖は抑制する。

## 設計

- `Type::Error` を `Type` に追加し、GUIDE §6.3 の各関数で「エラー型は何とでも一致し、性質の問い合わせでは保守的な値を返す」とする。`is_copy` などの結果が後続の誤検出を招かないよう、エラー型を含む値の所有権は検査しない。
- 回復の範囲は式単位から始め、名前解決エラー（未定義の名前）と型不一致を最初の対象にする。
- `SemanticIndex` は回復した部分の型を記録し、hover と G12 の補完に使えるようにする。

## 実装手順

1. **`Type::Error` の導入**: 単一化・表示・性質。確認: 既存の全診断テストが同じ結果（エラーのないプログラムの IR は不変）。
2. **名前解決と型不一致の回復**: 確認: `tests/diagnostics.rs` で一関数内の独立した 2 つのエラーを報告し、二次エラーがない。
3. **制御構文と計算式**: match・ループ・ビルダー展開内の回復。確認: 深さ上限と既存のスタック制約（2 MiB のテストスタック）。
4. **LSP 連携**: 確認: 壊れた関数内の別の式で hover が型を返す。
5. **Phase 2／3 の設計レビュー**。

## テスト計画

- 二次エラーの抑制を重点的に検査する（型不一致の連鎖、未定義名の使用の連鎖）。
- エラーのないプログラムで IR・診断・性能が変わらないこと。

## ドキュメント

- `docs/language.md` の診断、`_docs/tools/diagnostics.md`、`docs/architecture.md` の不変条件。

## 受け入れ条件

- [ ] 一つの関数の中の独立した複数の型エラーを一度に報告し、二次エラーを出さない。
- [ ] `Type::Error` がコード生成に到達しない。

## 落とし穴

- 大きな型検査関数に分岐を足すとスタックフレームが大きくなり、既存の深さテストが失敗する（リポジトリの既知の注意点）。回復処理は小さな補助関数へ分ける。
- `Type::Error` を含む制約を型クラス解決へ渡すと、誤った「インスタンスがない」エラーが出る。制約の解決から除外する。

## 対象外

- 自動修正の提案（G12 の code action で扱う）、構文エラーのあるファイルの型検査（Phase 2 まで）。

## 未決事項

- **所有権検査の扱い**: 既定案は Phase 1 ではエラー型を含む関数の所有権検査を行わない。
