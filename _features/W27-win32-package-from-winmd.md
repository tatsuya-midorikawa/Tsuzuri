## 実装者向け早見

## 目的

W13〜W25 がそろうと、Win32 の API を C と同じ意味で、型付きで宣言できる。しかし宣言そのものを手で書く限り、`[Out]` の付け忘れ、`BOOL` と `bool` の取り違え、長さの型、NULL を取れる引数、解放関数の誤りが、宣言の数だけ入りうる。C#・Rust・Zig は、Microsoft の win32metadata（Win32 の API を ECMA-335 のメタデータで記述したもの）から宣言を生成してこれを避けている。

このチケットは、Tsuzuri の FFI の型で表せる範囲を win32metadata から機械的に生成し、表せない宣言は推測せずに理由付きで省く（GUIDE §1 規則 2、`tsuzuri bindgen` と同じ）。利用者の依頼「改善が必要なものはあなたが考える中で最も良いと考えられる方法で」に従い、生成器の置き場・読み方・配布の形の案を比べて既定案を 1 つにした（決定事項と「採らなかった案」）。

## 現状（HEAD `fa40eede` で確認）

- **winmd を読む部品はない**。`grep -rn "winmd\|ECMA-335" src` は 0 件。
- **C のヘッダーからの `tsuzuri bindgen` は Windows を受けない**: `bindgen::lp64_target`（`src/bindgen.rs` 246 行）は `windows`・`mingw`・`cygwin` を含む triple を拒み、`src/bindgen_driver.rs` が `E2002`（`bindgen_unsupported_target`、`bindgen supports only 64-bit LP64 targets (Linux x64/ARM64 and macOS ARM64)`）を出す。型の表も LP64（`long` を `i64`。docs/language.md の「C ヘッダーからの生成」）で、Windows の LLP64（`long` は 32 bit）と合わない。
- **bindgen の出力の約束**: 1 行目の `MARKER`（`// Generated by tsuzuri bindgen. Do not edit.`、`src/bindgen.rs` 21 行）、`@trusted` を付けない理由の `TRUSTED_NOTE`（24 行。E15）、表せない宣言の `// skipped <C の名前>: <理由>` と警告 `W2002`（`bindgen_skipped_declaration`）、`MARKER` で始まるファイルだけを上書きする出力の保護（それ以外は `E2003`、`bindgen_output_not_generated`）、名前の変換（関数と field は snake_case、型は PascalCase、定数は C の名前のまま、予約語などは末尾に `_`）。
- **パッケージ**: git の依存はリポジトリのルートの `Tsuzuri.toml` とソースを読む（docs/language.md の「git 依存と Tsuzuri.lock」）。git・registry のパッケージは `[native]` を持てない（`src/driver.rs` の `git and registry packages cannot declare [native] link settings`、公開は `src/fetch.rs` の `a published package cannot declare [native] link settings`）。システムのライブラリの指定は W17 の `@link` が要る。パッケージのグラフのソースは 4,096 個まで（`src/driver.rs` の `load_from_root`）。
- **依存のモジュールはすべて型検査される**: 依存 `lib` の使わないモジュール `Unused.tz` に型の誤り（`def bad :: unit -> i64 = \() -> "x"`）を置くと、`lib/Used.tz` だけを使うアプリの `target/debug/tsuzuri.exe check app` が `lib/Unused.tz` の `E1003` で失敗した。frontend cache は構文解析の結果だけを保存する（`src/frontend_cache.rs` の冒頭の注釈）ので、型検査は毎回走る。
- **大きなモジュールの型検査の目安**（開発版 `target/debug/tsuzuri.exe`、opt-level 1、この作業機、閾値ではない）: `@trusted extern "FnN" def fn_N :: ref Hwnd -> i32u -> i64 -> i64 -> i64` を 5,000 個と `const C_N: i32 = N` を 20,000 個持つ 1 つのモジュール（905 KB）を使うプロジェクトの `check` は、1 回目 3.3 秒、2 回目 1.4 秒。win32metadata の全体の宣言の数はこれより多いと見込むが、数えていない（未確認。手順 1 で数える）。
- **名前空間の外側への補い（再現）**: 一時ディレクトリに `Win32/Foundation.tz`（`record Hwnd { value: i64 }`）、`Win32/System/Foo.tz`（`def x :: unit -> i64 = \() -> 40`）、`Win32/UI/Shell.tz`（`System::Foo.x () + 2` と `Foundation.Hwnd` を使う）、`Win32/UI/Shell/Common.tz`（`System::Foo.x () + UI::Shell.y ()` と `Foundation.Hwnd` を使う）、`Main.tz`（`Win32::UI::Shell::Common.z ()` を返す）を置くと、`check` は 0、`run` の終了コードは 82（= 40 + 42）。2 段の道筋（`System::Foo`）も外側へ補われ、同じ道筋のモジュール（`Win32/UI/Shell.tz`）と名前空間（`Win32/UI/Shell/`）は共存できる。winmd の `Windows.Win32.UI.Shell` と `Windows.Win32.UI.Shell.Common` はこの形になる。
- **条件付きの宣言はない**: target ごとにソースを分ける手段は「別の `--target`。使えない API はエラー」（`_tsuzuri/language-reference/compiler/directives.md` の比較の表）。x64 と ARM64 で配置の違う構造体を 1 つのソースに書けない。
- **std と方針**: std はコンパイラに埋め込まれ、予約モジュール名は 73 個（`src/stdlib.rs`）。std の公開関数は D-59（対象は最後）に従い、`tests/std_argument_order.rs` が検査する。GUI フレームワークの同梱は非目標（strategy.md、`_features/README.md` の「採用しない改善」）。D-63 は Win32 の宣言を std の外の公式パッケージにする案を W27 の既定案とした。
- **`@trusted` と `W1010`**: `@trusted` は「人がその外部関数の契約を確かめた」印で、`tsuzuri bindgen` は付けない（E15、docs/language.md の「ホスト関数のインポート」）。印のない `extern` を `extern` でない関数が参照すると、`tsuzuri audit` は全パッケージの宣言に `W1010` を出す（`src/capabilities.rs` の `untrusted_externs`）。依存のパッケージのソースはルートの作者が書き換えられないので、依存の印のない `extern` の `W1010` はルートからは消せない。
- **import library**: 同梱の zig の `lib/libc/mingw/lib-common/` に 783 個の `.def`（`.def.in` を含む）があり、うち 389 個が `api-ms-win-*`。`user32.def.in`・`gdi32.def`・`comctl32.def`・`comdlg32.def`・`ole32.def.in`・`uiautomationcore.def` などもある。SDK 10.0.26100 の `um/x64` に `Ole32.Lib`・`UIAutomationCore.lib` などがある（W25 の「現状」）。
- **依存できる crate**: `Cargo.toml` の依存は `rustc_apfloat`・`serde_json`（と任意の Cranelift）だけで、新しい crate は足さない（GUIDE §1 規則 10）。`unsafe` は `unsafe_code = "forbid"`。

### 1. コマンド（Phase 1）

```text
tsuzuri bindgen --winmd FILE --api LIST -o DIR [--json]
```

- `--winmd` は C のヘッダーの位置引数と同時に書けない（`E2000`、既存の `bindgen_argument_error`）。`--include-dir`・`--buffer`・`--consume` も `--winmd` とは使えない（`E2000`）。`--api` と `-o` は必須。
- Clang を使わないので、どの OS の上でも動く（`lp64_target` の判定は通らない）。生成物の対象は Windows の x86-64 と AArch64。
- `--json` は既存の bindgen と同じく診断を JSON にする。

### 2. 許可の一覧（`--api`。Phase 1）

- 1 行に 1 つ。`#` から行末は注釈。空行は読み飛ばす。
- 形: 完全な名前（`CreateWindowExW`・`WNDCLASSEXW`・`IFileOpenDialog`・`WM_PAINT`）、末尾の `*` の接頭辞（`WM_*`。定数と関数だけ）、名前空間（`Windows.Win32.UI.Shell.*`）。
- 閉包: 一覧の関数・構造体・interface が署名と field で参照する型（構造体・ハンドル・enum・コールバック・基底の interface）を推移的に足す。定数は自動では足さない（一覧に書いたものだけ）。
- 一覧の名前が winmd に無い・形が誤り（`E2000`、kind 案 `bindgen_unknown_api`）。閉包が 65,536 個を超える（`E1017`、`bindgen_api_limit`）。

### 3. 出力の配置と名前（Phase 1）

- winmd の名前空間 1 つにつき 1 つのモジュール。`Windows.Win32.` を除いた残りの最後の要素がモジュール名、その前がディレクトリ（`Windows.Win32.UI.WindowsAndMessaging` → `DIR/UI/WindowsAndMessaging.tz`）。公式パッケージは `namespace = "Win32"` のマニフェストと `-o .` で、利用者のプロジェクトでは `-o Win32` で、どちらも `…::Win32::UI::WindowsAndMessaging` になる。
- モジュール名が std の予約名（`Com`・`IO`・`Time` など。生成の時点の `RESERVED_MODULES` と、W25 が足す `Com`）と同じなら末尾に `_`（`System/Com_.tz`）。
- 別のモジュールの名前は、ルート `Win32` からの名前空間の道筋で書く（`Foundation.Hwnd`、`System::Com_.IStream`）。名前空間は外側へ順に補って解決される（docs/language.md の「名前空間」と現状の再現）ので、どちらの置き場でも同じ宣言に届く。生成器は、ある参照がより内側の生成したモジュールに先に当たらないことを自分の出力の全体で確かめ、当たるなら `E2002`（kind 案 `bindgen_ambiguous_module`）で止める。
- 宣言の名前は `tsuzuri bindgen` と同じ規則（関数・field・メソッドは snake_case、型は PascalCase、定数は C の名前のまま、衝突と予約は末尾に `_`）。interface の連鎖の中で同じ名前になるメソッド（Direct2D の派生の `CreateBitmap` など）は、派生の側に `_2`・`_3` を付ける（W25 の `E1001` を避ける）。

| `Windows.Win32.System.Com.IUnknown`（IID `00000000-0000-0000-C000-000000000046`。winmd では自分の 3 つの MethodDef を持つ TypeDef） | 生成しない。参照はすべて W25 の組み込みの `Com.IUnknown` に写し、その 3 つのメソッドを派生の interface のスロットに数えない（数えると全スロットが 3 ずれる）。名前ではなく IID で見分ける | W25 |

### 5. 生成しないもの（`// skipped` と `W2002`。Phase 1）

推測で別の型に写さず、宣言の位置に `// skipped <名前>: <理由>` を書いて `W2002`（既存の `bindgen_skipped_declaration`）を出す。

| 対象 | 理由の文（案） |
| --- | --- |
| ANSI の関数（`PSTR`・`PCSTR` を取る `…A`） | `ANSI variant; use the W function` |
| union と、union の field を持つ構造体（明示の FieldLayout） | `union (no union layout in Tsuzuri)` |
| x64 と ARM64 で配置か存在が違う宣言（`[SupportedArchitecture]`） | `architecture-specific layout` |
| 可変長引数、値で返す構造体、値で渡す構造体（[W36](W36-c-layout-by-value.md) が入る前。入った後は、W36 が対応する target では `ref` の無い `@c_layout` record に写す） | `by-value struct` など |
| `INVALID_HANDLE_VALUE`（-1）を失敗の値に持つハンドルの結果 | `invalid handle value -1 is not representable` |
| `[NullNullTerminated]`・`[MemorySize]` の buffer、`[NativeArrayInfo]` の無いポインター | `pointer without a length` |
| 文字列の定数 | `string constant`（`ZString` の定数の形が決まるまで） |
| 前提のチケットの型が無い宣言 | `needs <W番号>`（S4） |

### 6. 決定性と出力の保護（Phase 1）

- 各ファイルの先頭: `MARKER`、`// winmd: <ファイル名> sha256=<16 進>`、`// api: <一覧のファイル名> sha256=<16 進>`、`// target: windows x86_64 aarch64`、`TRUSTED_NOTE` の趣旨の行。絶対パス・日時を入れない。
- 宣言の並びは winmd の表の順ではなく、名前空間ごとに種類（定数 → enum → ハンドル → 構造体 → コールバック → interface → 関数）と名前のバイト順で決める（`BTreeMap`）。同じ入力から同じバイト列。
- `MARKER` で始まるファイルだけを上書きし、それ以外は `E2003`（`bindgen_output_not_generated`）。一覧から外れて生成しなくなったモジュールの古いファイル（`MARKER` で始まるもの）は消す。

### 7. 読み取り（`src/winmd.rs`。Phase 1）

- PE のヘッダー → CLI ヘッダー（データディレクトリ 14） → メタデータのルート（`BSJB`） → ストリーム `#~`・`#Strings`・`#Blob`・`#GUID`。
- `#~` のヒープの大きさの印と行の数から、ECMA-335 II.22 のすべての表（0x00〜0x2C）の行の大きさと coded index の幅を求める（使わない表も、後ろの表の位置を求めるために大きさを知る）。使う表は Module・TypeRef・TypeDef・Field・MethodDef・Param・InterfaceImpl・MemberRef・Constant・CustomAttribute・ClassLayout・FieldLayout・ModuleRef・TypeSpec・ImplMap・NestedClass。
- 署名（II.23.2）: メソッド・field の署名と型の符号化（`ELEMENT_TYPE_*`、`PTR`、`VALUETYPE`・`CLASS` の TypeDefOrRef、`ARRAY`・`SZARRAY`）。カスタム属性（II.23.3）: prolog `0x0001`、構築子の署名による固定引数、名前付きの引数。win32metadata の属性（`NativeTypedefAttribute`・`RAIIFreeAttribute`・`NativeArrayInfoAttribute`・`ConstAttribute`・`ComOutPtrAttribute`・`SupportedArchitectureAttribute`・`GuidAttribute` など）は完全な名前で照合する（名前と引数の並びは手順 1 で本物の winmd の CustomAttribute 表から確かめる）。
- 安全: すべての読み出しは範囲を検査して `Result` を返す（`unsafe` なし）。ファイルは 256 MiB まで（`bindgen::MAX_AST_BYTES` と同じ）、署名の入れ子は 32 まで、行の番号は表の行の数を超えない。違反は `E2002`（kind 案 `winmd_unreadable`、位置は入力のファイル）。

### 8. Phase 2: 公式パッケージ

- このリポジトリと同じ所有者の別の git リポジトリ（名前は D9 で決める）。ルートに `Tsuzuri.toml`（`name = "win32"`、`namespace = "Win32"`、版）、`api.txt`（GUI の核の一覧）、生成したモジュール、出どころ（winmd の版と SHA-256、生成に使った `tsuzuri` の版）とライセンスの表示（着手条件の記録に従う）を書いた README。
- GUI の核: wWinMain を持つ C のアプリと同じことに要る宣言（窓・メッセージ・GDI の描画・タイマー・DPI・コモンコントロール・ファイルダイアログ・COM の初期化）。正確な一覧は手順 1 の計測（S3）で決め、記録する。それ以外の API は、利用者が `tsuzuri bindgen --winmd` で自分のプロジェクトに生成する。
- 生成はそのリポジトリの CI が、記録した版の `tsuzuri` と winmd で行い、生成物に差が出ないこと（`git diff --exit-code`）と、Windows で小さな GUI のアプリ（W06 の基盤の形）が `check`・`build`・実行できることを確かめる。
- 利用: アプリのマニフェストに `win32 = { git = "https://…", rev = "<40 桁>", capabilities = ["ffi"] }`（権限のポリシーを有効にするとき）。`[native]` は要らない（W17 の `@link`）。`tsuzuri publish` の条件（`[native]` なし）も満たす。

### 9. Phase 3: ルートが依存の `extern` を信頼する印（決定事項 D5）

- ルートのマニフェストの直接の依存の項目に `trusted = true`（`native = true` と同じく、ルートが 1 つずつ書く。依存の依存は自分では書けない）。
- 意味: その依存が宣言した `@trusted` のない `extern`（関数・`extern view`・`extern interface`）について、`tsuzuri audit` は `W1010` を出さず、`extern` の行の `trusted` を `"dependency"`（text は `trusted (dependency)`）にする。`--warn untrusted-extern`（ルートの宣言だけ）と `@trusted` の性質の効果（E15 の Phase 4）は変えない。`tz-audit/1` には値を足すだけ。
- 依存の版（`rev`・`version`）を変えたとき、印は残る。印は「この出どころの公開者の確認を受け入れる」ことで、`audit` の報告は版を表示し続ける。

### 採らなかった案

| 案 | 採らなかった理由 |
| --- | --- |
| winmd を別の前処理で JSON にしてから読む（.NET の `System.Reflection.Metadata` の小さな道具、または第三者の JSON の写し） | 生成に .NET SDK か第三者のデータの版と利用条件が加わり、利用者が自分で生成できなくなる。JSON は winmd より大きく、版のずれも生む。ECMA-335 の読み取りは表・署名・属性の 3 つで、範囲を検査する Rust で書ける |
| 生成器をこのリポジトリの保守の道具だけにする（`tsuzuri` に入れない） | 依存のモジュールはすべて型検査されるので（現状）、公式パッケージは核に絞るしかない。核にない API を使う利用者は自分で生成できなければ手で書くことになる。CsWin32 と同じく、利用者が一覧を書いて生成する形が要る |
| win32metadata の全体を 1 つの公式パッケージにする | 毎回の `check` で数万の宣言を型検査する（現状の目安）。モジュールを分けても依存のモジュールはすべて検査される |
| std の `Win32` にする | GUI の非目標（strategy.md）、D-59（C の順の引数を std に入れるには 5 つ目の例外が要る）、std はコンパイラに埋め込まれ Windows 以外でも配られる |
| コンパイラに依存のモジュールの遅延の読み込みを足す | 「すべてのモジュールを検査する」規則（docs/language.md の「1 ファイル = 1 モジュール」）を変える大きな変更で、このチケットの範囲を出る |
| 生成器が `@trusted` を付ける／生成したファイルの印で `W1010` を消す | `@trusted` は人が確かめた印（E15）で、メタデータは返したハンドルの所有やコールバックの寿命を表さない。ファイルの中の印はパッケージの自己申告で、信頼の根拠にならない（D5 はルートが決める） |

## 落とし穴

- **`IUnknown` を普通の interface として生成しない**: winmd の `IUnknown` は自分の `QueryInterface`・`AddRef`・`Release` を MethodDef として持つ。`extern interface IUnknown : Com.IUnknown` を出すと、それを基底にする全 interface のスロットが 3 ずれ、すべての呼び出しが別のメソッドに飛ぶ。IID で見分けて `Com.IUnknown` に写す。`IDispatch` などほかの基底は普通に生成する。テストの `Fixture.cs` にも同じ IID の `IUnknown` を置き、派生のスロットの番号を確かめる。
- **`BOOL` は `i32`**: `bool` にすると `GetMessageW` の `-1`（失敗）が真になる。
- **`LPARAM`・`WPARAM` の符号**: `LPARAM` は `LONG_PTR`（符号あり）、`WPARAM` は `UINT_PTR`（符号なし）。
- **`[Optional]` と NULL**: `[Optional]` の無いポインターに NULL を渡せる API もある（文書だけで許すもの）。メタデータに従い、推測で `Maybe` にしない。
- **ハンドルの所有**: メタデータの `RAIIFree` は型の性質で、関数ごとの所有ではない（`GetStockObject` の結果を `DeleteObject` してはいけない）。生の型を `copy` にし、包みは利用者が明示する。
- **ImplMap の名前**: 関数の名前と `EntryPoint` が違うことがある。リンク名は `EntryPoint` を使う。
- **api-set の DLL**: `api-ms-win-*` の名前は MinGW と MSVC で使える import library が違いうる。手順 1 の表で写す。
- **アーキテクチャ**: x64 と ARM64 で違う構造体を 1 つのソースに書けない。片方だけを生成しない（`// skipped`）。
- **予約名**: 生成の時点の `RESERVED_MODULES` を見る。W25 の `Com` のように、後から予約名が増えると生成物のモジュール名が `E1011` になるので、公式パッケージの CI が新しい `tsuzuri` で生成し直す。
- **一覧の閉包の大きさ**: 名前空間を丸ごと書くと大きくなる。上限は `E1017` で止める。

## 対象外

- WinRT（`Windows.winmd`、`HSTRING`、activation factory）、`Windows.Wdk`（ドライバー）の名前空間。
- C のヘッダーからの `tsuzuri bindgen` の LLP64 への対応（winmd の方が型の情報が多い）。
- union の配置、値で返す構造体（W36 の後の `extern def` と、W25 の Phase 3 の interface のメソッドを除く）、可変長引数。
- 公式パッケージの宣言に人が `@trusted` を付けていく作業と、宣言の上の安全な包み（GUI のフレームワーク。非目標）。
- 公式パッケージを std や同梱のツールチェーンに含めること。
