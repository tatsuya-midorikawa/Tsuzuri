# スタックとヒープ

Tsuzuri では、値がスタックとヒープのどちらに置かれるかが、生成の書き方で決まります。`new` の有無を見れば、確保の場所をコードから読めます。

`new` を付けないリテラルは、いまの関数のスタックに置かれます。`new` を付けた配列やリストはヒープに置かれます。スタック上の値がスコープの外へ出るときは、コンパイラがヒープへコピーしてから渡すので、無効なスタックポインタは残りません。

## この記事のポイント

- `new` を使わないリテラル（配列・リスト・レコードなど）は現在の関数スタックフレームに直接確保されます。
- `new` を付与した配列やリスト（`new [...]`、`new [|...|]`）はヒープ領域に一括確保されます。
- 動的な長さを持つ配列は `new [T](length, initializer)` でヒープに生成します。
- スタック上の値が関数の戻り値や引数などで外部へ移動する際、自動的にヒープへ昇格されます。
- 文字列リテラルは実行ファイルの静的な読み取り専用領域を参照し、追加の確保はしません。
- 再帰的な共用体の子ノードは、コンストラクタがヒープへ確保します。
- `Rc.new`／`Arc.new` は、計数と値を入れたブロックをヒープへ確保します（[Rc と Arc](../built-in-types-and-modules/rc.md)）。
- 配列やリストの暗黙のディープコピーは `--warn implicit-copy`（`W1006`）で見つけられます。詳しくは [所有権とムーブ](ownership.md) を見てください。
- `tsuzuri build --allocator` でヒープの確保先を切り替えられます。実行ファイルの既定は `system` のままです。

## 記憶域の決定（new の有無）

値がどこに置かれるかは、生成の書き方で決まります。

| 生成構文 | 確保される記憶域 | 特徴 |
| --- | --- | --- |
| `[1, 2, 3]` / `[\|1, 2, 3\|]` | スタック領域 | 関数フレーム内にインライン確保。アロケーションコストなし |
| `Point { x: 1, y: 2 }` / `(1, "a")` | スタック領域 | レコードやタプルは値型としてスタック上にインライン配置 |
| `new [1, 2, 3]` / `new [\|1, 2, 3\|]` | ヒープ領域 | ヒープ上に要素領域を一括確保 |
| `new [T](length, initializer)` | ヒープ領域 | 実行時に動的なサイズを決定してヒープ確保 |
| `"hello"`（文字列リテラル） | 静的領域 | 静的バイナリの読み取り専用領域を参照（コピーなし） |
| `[]` / `[\|\|]` / `""`、`new [\|\|]` | メモリ領域なし | ポインタは null、長さ 0。空の配列リテラルは型注釈が必要です |
| `new []` | ヒープ領域 | 長さ 0 でも 1 バイト以上のアドレスを確保します。`new [\|\|]` とは違います |
| スカラー演算（整数や浮動小数の `a + b`） | レジスタまたはスタック | ヒープは使いません |
| 所有バッファを作る関数の結果（文字列連結など） | ヒープ領域 | 呼び出し先が確保したバッファを返します |

スタックとヒープのどちらに置いても、静的型は同じです。`[1, 2, 3]` も `new [1, 2, 3]` も `[i64]` で、同じ関数へ渡せます。記憶域の違いで、評価順序や所有権の規則は変わりません。

## スタック配置の基本

ローカル変数に直接記述されたリテラルは、ヒープアロケータを呼び出さず、現在の関数のスタックフレーム上に高速に確保されます。

```tsuzuri run=6
def sum_local :: unit -> i64 = \() ->
    let values = [1, 2, 3]
    values[0] + values[1] + values[2]

sum_local ()
```

実行結果:

```text
6
```

スコープを抜けるとスタックポインタが戻るので、バッファ自体の解放呼び出しはありません。要素が持つ子リソースだけは、通常どおり解放されます。短時間の作業データは、スタックに置いたまま読む方が確保を減らせます。

スタック上に配置できる 1 つのリテラルのデータサイズは、入れ子リテラルを含めて最大 64 KiB までです。このサイズを超える巨大なリテラルは、コンパイラによって自動的にヒープ領域へ退避されます。

## ヒープ配置と new 構文

スコープを超えて長期間生存するデータや、サイズの大きなコレクションは、明示的に `new` を付けてヒープ領域に確保します。

```tsuzuri run=42
let values = new [10, 20, 12]
values[0] + values[1] + values[2]
```

実行結果:

```text
42
```

> [!NOTE]
> `new` は、可変長の配列とリストをヒープに置く構文です。レコード、タプル、固定長配列 `[T; N]` には直接付けられません。固定長配列との組み合わせは `E1005` です。ヒープに置きたいときは `new [point]` のように、コレクションの要素にします。`new` の内側のリテラルもヒープに確保されます。

## 実行時に長さを決めて配列を作る

配列の要素数がコンパイル時に定まらない場合は、`new [T](length, initializer)` 構文を使用します。第 1 引数に要素数、第 2 引数にインデックスを受け取って要素を生成するラムダ式を指定します。

```tsuzuri run=12
let sized = new [i64](4, \i -> i * 2)
sized[1] + sized[2] + sized[3]
```

実行結果:

```text
12
```

この構文で生成された配列は、実行時に指定された要素数分のバッファをヒープ上に直接確保して初期化します。

## スタックからヒープへの自動昇格（ヒープ退避）

スタック上に確保された値が宣言元のスコープを抜け出す場合、Tsuzuri は要素データを自動的にヒープ領域へ退避（昇格）させます。

具体的には、以下の操作を行ったタイミングで自動昇格が発生します。

- 関数の戻り値として返却する
- 値渡しの引数として別の関数へ渡す
- 別の変数や可変変数（`let mut`）へムーブする
- クロージャや並行タスク（`task`）へ捕捉する
- 別のコレクションの要素として格納する
- 排他借用（`ref mut`）として貸し出す（置換可能にするため）

```mermaid
flowchart LR
    subgraph 関数のスタック
        Stack["スタック上の配列<br>[1, 2, 3]"]
    end
    Stack -->|関数の外へ返却| Promote["自動昇格（ヒープ退避）"]
    subgraph ヒープ領域
        Promote --> Heap["ヒープ上の配列<br>[1, 2, 3]"]
    end
    Heap --> Return["呼び出し元が所有"]
```

```tsuzuri run=3
def make_data :: unit -> [i64] = \() ->
    let local = [1, 2, 3]
    local

let escaped = make_data ()
escaped.length
```

実行結果:

```text
3
```

`local` はスタック上に作られますが、戻り値として出るときにヒープへ移されます。無効なスタックポインタを返す書き方は、コンパイル時に拒否されます。

一方で、共有借用（`ref x`）、インデックスアクセス `x[i]`、`.length` の参照、`for` ループによる走査は、スタック上のメモリを直接参照して行われるため、ヒープ退避は発生せずゼロコストです。

> [!TIP]
> 関数の外へ返却することがあらかじめ分かっているデータは、最初から `new [1, 2, 3]` と書いておくことで、昇格時のコピーコストを未然に回避できます。

## 文字列リテラルと空コレクション

文字列リテラル（`"hello"`）は、実行時にスタックやヒープを確保せず、実行ファイルの静的な読み取り専用領域を参照します。コピーは起きません。

空の `[]`、`[||]`、`""`、および `new [||]` は、ポインタが null で長さ 0 です。メモリは使いません。`new []` だけは違い、長さ 0 でも 1 バイト以上のアドレスをヒープに確保します。空の配列は型が決まらないので、`[i64]` のような注釈が必要です。

## 再帰的共用体のヒープ配置

木構造や連結リストなどの再帰的なデータ構造を表現する共用体（`union`）では、子ノードが自動的にヒープ領域へ動的確保されます。

```tsuzuri run=3
union Tree =
    | Leaf
    | Node of Tree * i64 * Tree

def rec count :: Tree -> i64 = \tree ->
    match tree with
    | Leaf -> 0
    | Node (left, _, right) -> 1 + count left + count right

let tree = Node (Node (Leaf, 2, Leaf), 1, Node (Leaf, 3, Leaf))
count tree
```

実行結果:

```text
3
```

`new` や、Rust の `Box` のような明示的なポインタは要りません。再帰のケースはコンパイラが検出し、子ノードの確保と解放を入れます。

再帰的な共用体の解放は、スタックを消費しないループで行います。深い木でも、解放のために関数スタックを要素数ぶん積むことはありません。

## コピーコスト

Copy な要素の配列やリストを、代入のあとも使うと、ヒープへのディープコピーになります。警告の出し方と、`Array.copy` / `List.copy` による明示コピーは [所有権とムーブ](ownership.md) にまとめてあります。ここでは繰り返しません。

## ホスト提供のアロケータ（--allocator）

ヒープの確保先は `tsuzuri build` の `--allocator` で選びます。`check` や `run` には付けられません。

```sh
tsuzuri build --emit object --allocator host Main.tz
```

| 値 | 動き |
| --- | --- |
| `system`（既定） | ネイティブでは C 標準ライブラリの `malloc` / `realloc` / `free`。WASM ではモジュール内のフリーリスト |
| `host` | ホストの `tsuzuri_host_alloc`、`tsuzuri_host_free`、`tsuzuri_host_realloc` に委譲する |
| `counting` | `system` を包み、確保回数、解放回数、使用中バイト、ピークバイトを数える。`tsuzuri_alloc_stats` で読む |

`host` と `counting` は、`--emit object`、`llvm`、`header`、または WASM だけで使えます。`--emit exe`、`wgsl`、`--trap-mode return` と一緒だと `E2000` です。`host` は `--wasm-feature threads` とも同時には指定できません。実行ファイルの既定ヒープは `system` のままです。

`--freestanding` は、C 標準ライブラリに依存しない native の `object` / `llvm` / `header` を出します。`--allocator host` が必須です。残ってよい外部は、ホストの allocator、自分で宣言した `extern`、`memcpy` / `memmove` / `memset` / `memcmp`、compiler-rt の整数ヘルパーだけです。IO、OS API、タスク、`Debug`、プログラム引数は `E2000` で拒否されます。

関数の契約とリンク方法は [ネイティブ連携 (C ABI)](../compiler/native-interop.md) と [コンパイラ オプション](../compiler/option.md) を見てください。

## 他の言語との比較

| 項目 | Tsuzuri | Rust | C / C++ |
| --- | --- | --- | --- |
| スタック配置 | リテラルで自動（`new` なし） | `let x = [...]` | `int arr[3];` |
| ヒープ配置 | `new [...]` または `new [T](n, f)` | `vec![...]` / `Box::new` | `malloc` / `new` |
| スコープ脱出時の昇格 | 自動（安全にヒープ退避） | コンパイルエラー | 未定義動作（ダングリング） |
| 再帰型の配置 | union で自動ヒープ配置 | `Box<T>` による明示ボクシング | ポインタで手動管理 |
| アロケータ切り替え | `--allocator` オプション | `#[global_allocator]` | アロケータ差し替え |

## まとめ

- `new` なしで生成した値はスタックに、`new` を付けたコレクションはヒープに確保されます。
- 動的な長さの配列は `new [T](length, initializer)` でヒープ上に生成します。
- スタック上の値がスコープの外へ移動する際は、自動的にヒープ領域へ安全に昇格されます。
- 文字列リテラルは静的な読み取り専用領域を参照します。空の `[]` や `[||]` はメモリを使いません。`new []` だけは長さ 0 でもヒープにアドレスを取ります。
- 再帰的な union の子ノードは自動的にヒープ確保され、スタックを浪費しません。
- 暗黙のコレクション複製は `--warn implicit-copy`（`W1006`）で見つけられます。
- `--allocator host` と `--freestanding` は `build` のオブジェクト出力向けです。実行ファイルの既定にはなりません。
