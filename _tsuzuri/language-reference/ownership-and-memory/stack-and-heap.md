# スタックとヒープ

Tsuzuri では、値がスタックとヒープのどちらに置かれるかが、生成の書き方で決まります。`new` の有無を見れば、確保の場所をコードから読めます。

`new` を付けないリテラルは、いまの関数のスタックに置かれます。`new` を付けた配列やリストはヒープに置かれます。スタック上の値がスコープの外へ出るときは、コンパイラがヒープへコピーしてから渡すので、無効なスタックポインタは残りません。

## この記事のポイント

- `new` を使わないリテラル（配列・リスト・レコードなど）は現在の関数スタックフレームに直接確保されます。
- `new` を付与した配列やリスト（`new [...]`、`new [|...|]`）はヒープ領域に一括確保されます（リストは要素数ちょうどの 1 つの chunk です）。
- 動的な長さを持つ配列は `new [T](length, initializer)` でヒープに生成します。
- スタック上の値が関数の戻り値や引数などで外部へ移動する際、自動的にヒープへ昇格されます。
- 文字列リテラルは実行ファイルの静的な読み取り専用領域を参照し、追加の確保はしません。
- 再帰的な共用体の子ノードは、コンストラクタがヒープへ確保します。
- `Rc.new`／`Arc.new` は、計数と値を入れたブロックをヒープへ確保します（[Rc と Arc](../built-in-types-and-modules/rc.md)）。
- 配列やリストの暗黙のディープコピーは `--warn implicit-copy`（`W1006`）で見つけられます。詳しくは [所有権とムーブ](ownership.md) を見てください。
- `tsuzuri build --allocator` でヒープの確保先を切り替えられます。実行ファイルの既定は `system` のままです。

## 記憶域の決定（new の有無）

値がどこに置かれるかは、生成の書き方で決まります。

| 生成構文 | 確保される記憶域 | 特徴 |
| --- | --- | --- |
| `[1, 2, 3]` / `[\|1, 2, 3\|]` | スタック領域 | 関数フレーム内にインライン確保。アロケーションコストなし |
| `Point { x: 1, y: 2 }` / `(1, "a")` | スタック領域 | レコードやタプルは値型としてスタック上にインライン配置 |
| `new [1, 2, 3]` / `new [\|1, 2, 3\|]` | ヒープ領域 | ヒープ上に要素領域を一括確保 |
| `new [T](length, initializer)` | ヒープ領域 | 実行時に動的なサイズを決定してヒープ確保 |
| `"hello"`（文字列リテラル） | 静的領域 | 静的バイナリの読み取り専用領域を参照（コピーなし） |
| `[]` / `[\|\|]` / `""`、`new [\|\|]` | メモリ領域なし | ポインタは null、長さ 0。空の配列リテラルは型注釈が必要です |
| `new []` | ヒープ領域 | 長さ 0 でも 1 バイト以上のアドレスを確保します。`new [\|\|]` とは違います |
| スカラー演算（整数や浮動小数の `a + b`） | レジスタまたはスタック | ヒープは使いません |
| 所有バッファを作る関数の結果（文字列連結など） | 原則ヒープ領域 | 下の確保の省略に該当しなければ、呼び出し先が確保したバッファを返します |

スタックとヒープのどちらに置いても、静的型は同じです。`[1, 2, 3]` も `new [1, 2, 3]` も `[i64]` で、同じ関数へ渡せます。記憶域の違いで、評価順序や所有権の規則は変わりません。

## 確保の省略とバッファ再利用

文字列リテラル同士の `+` は一つのリテラルとして生成し、`(left + right).length` は両辺を評価して長さを足します。
後者も overflow と文字列長の上限を検査し、両辺を通常と同じ順序で解放しますが、結果の文字列のためのヒープは使いません。
`string` をそのまま返す組み込み `to_string` を挟んでも、リテラルの連結・長さだけの連結・局所の記憶域には同じ最適化を適用します。
長さだけを求める場合も、連結長のオーバーフローなどのトラップ位置は、外側の `to_string` や `.length` ではなく元の `+` 式です。

```tsuzuri run=3
(to_string ("a" + "😀")).length
```

```tsuzuri run=11
let text = "hello" + " world"
text.length
```

外へ逃げない文字列連結の結果は、関数入口の 256 bytes の領域に置けます。容量は UTF-16 の `string` では
128 code unit、`TSUZURI_STRINGS=compact` で結果が Latin-1 の `string` では 256 code unit、`utf8string` では 256 bytes で、実行時に超えればヒープへ戻ります。
外へ逃げない局所の関数値の捕捉環境も、保守的な大きさが 1 KiB 以下なら入口のスタックに置きます。
追加領域の予算は関数あたり合計 4 KiB です。再帰の循環に入る関数と Task の本体は対象外です。
値を返す・値渡しする・捕捉する・排他借用する束縛は、これらの最適化でスタックに置きません。
native Windows では、ローカル束縛の初期化で使う追加領域をスタックへ置かず、通常のヒープ経路を使います。これは保守的な実装上の fallback で、型や言語上の意味は変わりません。

連結で消費する左辺がヒープの所有バッファなら、`realloc` で伸ばして再利用します。リテラルの静的領域やスタック領域は
`realloc` に渡しません。文字列の記述子は容量を持たないので、繰り返し追記の償却定数時間を保証するものではありません。

確保失敗は環境に依存する資源の失敗で、確保を省いた箇所では発生しません。入力で決まるトラップ、評価順序、借用、
所有権、利用者の `Drop.drop` の順序は変わりません。スタック枯渇に至る再帰の深さは規定せず、コンパイラや最適化で変わります。
WASM のヒープ上限の指定は [WebAssembly](../compiler/webassembly.md) を参照してください。

## スタック配置の基本

ローカル変数に直接記述されたリテラルは、ヒープアロケータを呼び出さず、現在の関数のスタックフレーム上に高速に確保されます。

```tsuzuri run=6
def sum_local :: unit -> i64 = \() ->
    let values = [1, 2, 3]
    values[0] + values[1] + values[2]

sum_local ()
```

実行結果:

```text
6
```

スコープを抜けるとスタックポインタが戻るので、バッファ自体の解放呼び出しはありません。要素が持つ子リソースだけは、通常どおり解放されます。短時間の作業データは、スタックに置いたまま読む方が確保を減らせます。

スタック上に配置できる 1 つのリテラルのデータサイズは、入れ子リテラルを含めて最大 64 KiB までです。このサイズを超える巨大なリテラルは、コンパイラによって自動的にヒープ領域へ退避されます。

## ヒープ配置と new 構文

スコープを超えて長期間生存するデータや、サイズの大きなコレクションは、明示的に `new` を付けてヒープ領域に確保します。

```tsuzuri run=42
let values = new [10, 20, 12]
values[0] + values[1] + values[2]
```

実行結果:

```text
42
```

> [!NOTE]
> `new` は、可変長の配列とリストをヒープに置く構文です。レコード、タプル、固定長配列 `[T; N]` には直接付けられません。固定長配列との組み合わせは `E1005` です。ヒープに置きたいときは `new [point]` のように、コレクションの要素にします。`new` の内側のリテラルもヒープに確保されます。

## 実行時に長さを決めて配列を作る

配列の要素数がコンパイル時に定まらない場合は、`new [T](length, initializer)` 構文を使用します。第 1 引数に要素数、第 2 引数にインデックスを受け取って要素を生成するラムダ式を指定します。

```tsuzuri run=12
let sized = new [i64](4, \i -> i * 2)
sized[1] + sized[2] + sized[3]
```

実行結果:

```text
12
```

この構文で生成された配列は、実行時に指定された要素数分のバッファをヒープ上に直接確保して初期化します。

## スタックからヒープへの自動昇格（ヒープ退避）

スタック上に確保された値が宣言元のスコープを抜け出す場合、Tsuzuri は要素データを自動的にヒープ領域へ退避（昇格）させます。

具体的には、以下の操作を行ったタイミングで自動昇格が発生します。

- 関数の戻り値として返却する
- 値渡しの引数として別の関数へ渡す
- 別の変数や可変変数（`let mut`）へムーブする
- クロージャや並行タスク（`task`）へ捕捉する
- 別のコレクションの要素として格納する
- 排他借用（`ref mut`）として貸し出す（置換可能にするため）

```mermaid
flowchart LR
    subgraph 関数のスタック
        Stack["スタック上の配列<br>[1, 2, 3]"]
    end
    Stack -->|関数の外へ返却| Promote["自動昇格（ヒープ退避）"]
    subgraph ヒープ領域
        Promote --> Heap["ヒープ上の配列<br>[1, 2, 3]"]
    end
    Heap --> Return["呼び出し元が所有"]
```

```tsuzuri run=3
def make_data :: unit -> [i64] = \() ->
    let local = [1, 2, 3]
    local

let escaped = make_data ()
escaped.length
```

実行結果:

```text
3
```

`local` はスタック上に作られますが、戻り値として出るときにヒープへ移されます。無効なスタックポインタを返す書き方は、コンパイル時に拒否されます。

一方で、共有借用（`ref x`）、インデックスアクセス `x[i]`、`.length` の参照、`for` ループによる走査は、スタック上のメモリを直接参照して行われるため、ヒープ退避は発生せずゼロコストです。

> [!TIP]
> 関数の外へ返却することがあらかじめ分かっているデータは、最初から `new [1, 2, 3]` と書いておくことで、昇格時のコピーコストを未然に回避できます。

## 文字列リテラルと空コレクション

文字列リテラル（`"hello"`）は、実行時にスタックやヒープを確保せず、実行ファイルの静的な読み取り専用領域を参照します。コピーは起きません。

空の `[]`、`[||]`、`""`、および `new [||]` は、ポインタが null で長さ 0 です。メモリは使いません。`new []` だけは違い、長さ 0 でも 1 バイト以上のアドレスをヒープに確保します。空の配列は型が決まらないので、`[i64]` のような注釈が必要です。

## 再帰的共用体のヒープ配置

木構造や連結リストなどの再帰的なデータ構造を表現する共用体（`union`）では、子ノードが自動的にヒープ領域へ動的確保されます。

```tsuzuri run=3
union Tree =
    | Leaf
    | Node of Tree * i64 * Tree

def rec count :: Tree -> i64 = \tree ->
    match tree with
    | Leaf -> 0
    | Node (left, _, right) -> 1 + count left + count right

let tree = Node (Node (Leaf, 2, Leaf), 1, Node (Leaf, 3, Leaf))
count tree
```

実行結果:

```text
3
```

`new` や、Rust の `Box` のような明示的なポインタは要りません。再帰のケースはコンパイラが検出し、子ノードの確保と解放を入れます。

再帰的な共用体の解放は、スタックを消費しないループで行います。深い木でも、解放のために関数スタックを要素数ぶん積むことはありません。

## コピーコスト

Copy な要素の配列やリストを、代入のあとも使うと、ヒープへのディープコピーになります。警告の出し方と、`Array.copy` / `List.copy` による明示コピーは [所有権とムーブ](ownership.md) にまとめてあります。ここでは繰り返しません。

## WASM のヒープ

WASM の `system` アロケータは、モジュールに組み込まれた小さなヒープです。静的データとスタックの後ろ（`__heap_base`）から始まり、64 KiB のページ単位で `memory.grow` しながら、`--wasm-max-memory`（既定 16 MiB）の上限まで伸びます。

- 1 回の確保は、16 バイトのヘッダーと要求サイズを足して 16 の倍数に切り上げた大きさのブロックで、最小は 32 バイトです（16 バイトの要求は 32、17 バイトは 48 を使います。0 バイトの要求も 32 バイトを取ります）。ブロックは 16 バイト境界に置かれ、ペイロードも 16 バイト境界です。
- 解放したブロックは再利用されます。容量 528 バイト以下のブロックは、すぐには隣と結合せず、同じ容量の次の要求にすぐ返ります（後入れ先出し）。ほかの大きさの要求がヒープを伸ばさなければならないとき（と、`realloc` が隣の空きを必要とするとき）に、まとめて隣と結合して再利用できるようにします。大きいブロックは、解放の時に隣と結合します。
- ヒープの終端にあるブロックは、`Vec.push` などの再確保でその場で伸びます。コピーせず、アドレスも変わりません。ほかのブロックは、隣が空きなら吸収して伸び、そうでなければ新しいブロックへ `memory.copy` で移します。
- 解放したブロックが終端に触れていれば、ヒープの終端を戻します。`memory.grow` で増えたページはホストへ返せないので、増えたままです。ヒープが空になると、次の確保は `__heap_base` から再開します。
- 上限を超える確保、`memory.grow` の失敗はトラップです。`--trap-info` の種類は `allocation failed` で、threads でも同じです。1 回の要求は「上限 − 32 バイト」までです。
- 528 バイトより大きいブロックの探索は、空きブロックのアドレス順のリストを先頭から見て、最初に収まるものを使います。大きな空きブロックが多数に分かれたプログラムでは、確保と解放の時間がその数に比例します。小さなブロックは、リストの長さによらず一定です。ただし、64 KiB 以上で、しかも要求の 4 倍以上の残りを切り出すことになる空きブロックは飛ばして、先へ進みます。大きな空きブロック（穴）を中くらいのブロックで切り刻むと、同じ大きさの次の大きな要求が穴に収まらず、上限の 16 MiB を超えてしまうことがあるためです（matrix の計算で 6 MB の配列を解放したあとに 36 KB のブロックを確保し、再び 6 MB を確保するパターン）。飛ばすのは、最近の最大の要求の 2 倍までの空きブロックだけです（最近の最大の要求は、大きいブロックのリストを探すたびに 1/64 ずつ忘れます）。それより大きい穴は、最近のどの要求も近づいておらず、取っておくと、数十 KB のブロックを確保と解放するだけのプログラムでもヒープが上限まで伸びるので、普通のブロックと同じに切り出します。後ろに、そう切り刻まずに済むブロックがあれば、その最初のものを使います（大きな一時配列を解放しても、後ろに小さなブロックが生き残っていれば穴は残るので、次に同じ大きさかそれに近い要求が来たときに使われます）。どれもなければ、ヒープの終端を延ばせる間は終端から返し、延ばせなくなったら（上限の手前）、飛ばした最初のブロックから切り出します。穴を残すために終端を延ばすので、大きな一時配列（最近の要求に近い大きさの穴ができる）と長く生きる小さなブロックが混ざるプログラムは、生きているデータより大きなヒープを使い、上限の近くまで伸びることがあります。上限に届いたあとは、穴から切り出して続けます。

native の `system` は C 標準ライブラリのアロケータで、このヒープとは別です。

## ホスト提供のアロケータ（--allocator）

ヒープの確保先は `tsuzuri build` の `--allocator` で選びます。`check` や `run` には付けられません。

```sh
tsuzuri build --emit object --allocator host Main.tz
```

| 値 | 動き |
| --- | --- |
| `system`（既定） | ネイティブでは C 標準ライブラリの `malloc` / `realloc` / `free`。WASM ではモジュール内のヒープ（[WASM のヒープ](#wasm-のヒープ)） |
| `host` | ホストの `tsuzuri_host_alloc`、`tsuzuri_host_free`、`tsuzuri_host_realloc` に委譲する |
| `counting` | `system` を包み、確保回数、解放回数、使用中バイト、ピークバイトを数える。`tsuzuri_alloc_stats` で読む |
| `small` | native の 64-bit だけ。512 バイト以下をサイズ区分から返し、それより大きいものは C 標準ライブラリ（[ネイティブのサイズ区分 allocator](#ネイティブのサイズ区分-allocator)） |

`host` と `counting` は、`--emit object`、`llvm`、`header`、または WASM だけで使えます。`--emit exe`、`wgsl`、`wgsl-relaxed`、`spirv`、`spirv-relaxed`、`--trap-mode return` と一緒だと `E2000` です。`host` は `--wasm-feature threads` とも同時には指定できません。実行ファイルの既定ヒープは `system` のままです。

`--freestanding` は、C 標準ライブラリに依存しない native の `object` / `llvm` / `header` を出します。`--allocator host` が必須です。残ってよい外部は、ホストの allocator、自分で宣言した `extern`、`memcpy` / `memmove` / `memset` / `memcmp`、compiler-rt の整数ヘルパーだけです。IO、OS API、タスク、`Debug`、プログラム引数は `E2000` で拒否されます。

関数の契約とリンク方法は [ネイティブ連携 (C ABI)](../compiler/native-interop.md) と [コンパイラ オプション](../compiler/option.md) を見てください。

## ネイティブのサイズ区分 allocator

`--allocator small` は、native の 64-bit で小さなブロックの確保と解放を短い手順にするアロケータです。既定ではなく、`system` のままのプログラムには何も変わりません。

```sh
tsuzuri build --allocator small Main.tz
```

- 0 から 512 バイトの確保は、16 バイト刻みの 32 区分（16、32、……、512 バイトのブロック）から返します。ブロックにヘッダーはなく、先頭は 16 バイト境界です。513 バイト以上の確保と、`realloc` で大きくなったブロックは、`system` と同じ C 標準ライブラリの `malloc` / `realloc` / `free` が受け持ちます。
- 区分ごとに、1 MiB 境界の 1 MiB の region を持ちます。region は 1 つの区分のブロックだけを持ち、アドレスから区分がわかるので、解放にサイズは要りません。
- スレッドごとにキャッシュを持ち、確保と解放はロックもアトミック命令も使いません。キャッシュが空になると、中央のスタックから 4 KiB ぶんをまとめて受け取るか、region の未使用の部分から切り出します。キャッシュが溢れると、4 KiB ぶんを中央へ返します。中央のスタックは try-lock で守ります。ロックが取れなければ待たず、確保は `malloc` から、解放はキャッシュに残して次の解放で再試行するので、他のスレッドを待つことはありません。
- あるスレッドが確保したブロックを別のスレッドが解放してもかまいません。解放したスレッドのキャッシュに入り、その後はそのスレッドが使います。
- 確保に失敗した（C ライブラリが null を返した）ときは、`system` と同じく、その場でトラップします。
- メモリは OS へ返しません。終わったスレッドのキャッシュ（1 スレッドで約 264 KiB まで）は、ほかのスレッドから使われません。
- `Atomic` と `Mutex` のセルは、`system` と同じく 16 バイト境界に置かれます。ホストへ返した所有バッファは、`tsuzuri_free` で解放します。C の `free` へ渡してはいけません。

出力は、実行ファイル（`--emit exe`）、`object`、`llvm`、`header`、`shared` です。WASM は自前のヒープ（[WASM のヒープ](#wasm-のヒープ)）を使い続けるので `E2000` になります。`wgsl` と `spirv` の出力、`--trap-mode return`、`--freestanding` とも一緒には指定できません。

Windows（MSVC）で試験しているのは、実行ファイルと、アロケータの単体テスト（スレッドを含む）です。ランタイムを埋め込む COFF の `--emit object` は、`--allocator` に関係なく `E2002` で作れません。Windows の `shared` は試験していません。

1 つのプログラムにリンクした複数のオブジェクトは、1 つの状態を共有します（macOS と Linux。共有ライブラリは自分の状態を持ちます）。同じプログラムの中で `--allocator` を混ぜてはいけません。`system` のオブジェクトが `small` のブロックを `free` へ渡すと壊れます。共有ライブラリのブロックは、確保したその共有ライブラリの `tsuzuri_free` で解放してください（ELF で複数の共有ライブラリを読み込むと、`tsuzuri_free` が先に読み込んだほうへ解決されることがあります）。ASan の use-after-free の検出や leak checker は、ブロック 1 つ 1 つではなく、1 MiB の region の `malloc` 1 つを見ます。

コードは、確保するプログラムで約 2.5 KiB 増えます。`.bss` に約 130 KiB を使いますが、触るまで物理メモリにはなりません。確保と解放の呼び出しは、`system` の `malloc` と `free` と同じように、読まれないまま解放されるブロックを LLVM が取り除けます。

測定した範囲（Apple M1 Max、PX02 の app）では、`binary_trees`、`tree_transform`、`tokenize`、`csv_aggregate` のように小さなブロックを大量に確保して手放すプログラムの時間は `system` の 0.4〜0.65 倍で、macOS で `system` より遅くなった app は `closure_pipeline`（約 1.06 倍。確保が少なく、コードの配置の差と読めます）だけでした。ピーク RSS は macOS で同じです（スレッドのキャッシュなどの固定費で、小さなプログラムは 0.1〜0.15 MiB 増えます）。glibc では、16〜24 バイトの確保が多いプログラムで約 25% 小さくなります。

既知の制限: Linux（arm64、glibc）では、ほかの確保を済ませたプロセスで大きな配列の確保と解放を繰り返す `record_sort` が `system` の 1.7〜2.3 倍遅くなりました。命令数は同じで、ページフォールトが増えています。`system` では C ライブラリのヒープの末尾を小さなブロックが押さえているので、glibc は大きな配列を解放しても末尾を OS へ返しません。`small` は小さなブロックを region に置くので、末尾が空いて、解放のたびに glibc が返し、次の確保で取り直します（`strace` の `brk` で確認）。そのため既定にはしていません。数値、条件、測っていないこと（Linux x64・Windows、専用機の値）は [docs/benchmarks.md](../../../docs/benchmarks.md) にあります。

## 他の言語との比較

| 項目 | Tsuzuri | Rust | C / C++ |
| --- | --- | --- | --- |
| スタック配置 | リテラルで自動（`new` なし） | `let x = [...]` | `int arr[3];` |
| ヒープ配置 | `new [...]` または `new [T](n, f)` | `vec![...]` / `Box::new` | `malloc` / `new` |
| スコープ脱出時の昇格 | 自動（安全にヒープ退避） | コンパイルエラー | 未定義動作（ダングリング） |
| 再帰型の配置 | union で自動ヒープ配置 | `Box<T>` による明示ボクシング | ポインタで手動管理 |
| アロケータ切り替え | `--allocator` オプション | `#[global_allocator]` | アロケータ差し替え |

## まとめ

- `new` なしで生成した値はスタックに、`new` を付けたコレクションはヒープに確保されます。
- 動的な長さの配列は `new [T](length, initializer)` でヒープ上に生成します。
- スタック上の値がスコープの外へ移動する際は、自動的にヒープ領域へ安全に昇格されます。
- 文字列リテラルは静的な読み取り専用領域を参照します。空の `[]` や `[||]` はメモリを使いません。`new []` だけは長さ 0 でもヒープにアドレスを取ります。
- 再帰的な union の子ノードは自動的にヒープ確保され、スタックを浪費しません。
- 暗黙のコレクション複製は `--warn implicit-copy`（`W1006`）で見つけられます。
- `--allocator host` と `--freestanding` は `build` のオブジェクト出力向けです。実行ファイルの既定にはなりません。
- `--allocator small` は native の 64-bit 向けのサイズ区分 allocator で、実行ファイルにも付けられます。既定は `system` のままです。
