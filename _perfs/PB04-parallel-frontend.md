## 目的

構文解析・型検査・所有権検査・IR 生成を複数のコアで並列に実行し、Go のコンパイラのように CPU 数に応じてビルドを速くする。
出力は並列度によらずバイト単位で同じにする。

## 現状と計測

- フロントエンドは単一スレッドです。2026-09-29 のサンプリングでは、合成 1,000 モジュールの IR 出力（2.58 s）の間、主スレッド以外に処理はありませんでした。計測機は 10 コアです。
- 処理の順序: 全ファイルの読み込みと構文解析 → 全モジュールの名前の収集 → シグネチャ → 本体の型検査 → 所有権検査 → 単相化 → closure lowering → 所有権検査 → IR 生成（docs/architecture.md）。
- 決定性のため、名前の集合などに `BTreeMap`／`BTreeSet` を使っています（GUIDE §1.5）。
- 並列コード生成（LLVM 側）は G17 Phase 1 で計画しています。

## 目標と指標

- 目標: 10 コアで、124K 行の `check` を単一スレッドの 1/5 以下の時間にする（PB02 の改善後の値に対して）。
- 指標: スレッド数ごとの段階別時間、スケーリング、最大 RSS。

## 施策

- 構文解析: ファイルごとに独立しているため、ファイル単位で並列に実行する。
- 型検査: 名前とシグネチャの収集（全体の情報）の後、関数の本体の検査を関数単位で並列に実行する。ジェネリック関数の具体化の要求は各スレッドで集め、決定的な順序でまとめる。
- 所有権検査と closure lowering: 関数単位で並列に実行する。
- IR 生成: 関数ごとに別の buffer へ出力し、関数 ID の順に連結する。
- 並列化は Rust 標準の `std::thread::scope` で行い、スレッドのスタックの大きさを明示する（深い再帰の上限のテストと整合させる）。依存 crate（rayon など）を使う場合は承認を得る。

## 意味・安全性の保持

- 診断の内容と順序（ソース ID・位置・コード・メッセージの安定順）、型付き IR、生成 IR を、スレッド数によらず同一にする。
- 共有データは読み取り専用にし、各スレッドの結果は決定的な規則で結合する。`unsafe` は使わない。

## 検証

- スレッド数 1・2・並列最大で、全テストの IR・診断が同一であること。
- 故意に処理時間をずらした場合（テスト用の遅延）でも出力が同一であること。
- スケーリングを記録する。

## 受け入れ条件

- [ ] スレッド数によらず出力が同一で、全テストが通る。
- [ ] コア数に応じた短縮を実測し、記録している。

## リスク

- 型推論の状態（`Inference`）や単相化の要求表は共有されやすい。関数単位で独立させるための API の分割が必要になる。
- スレッドごとの確保で最大 RSS が増える。PB02 の arena と合わせて計測する。

## 対象外

- LLVM の並列コード生成（G17）、複数マシンでの分散ビルド。
