## 目的

「Go を上回る超高速ビルド」を判断するため、規模と構造をそろえたプロジェクトで、Tsuzuri と Go・Zig・Rust・C/C++ のビルド時間とコンパイラのメモリを比較する。
ビルドの段階別の内訳を記録し、PB チケットの優先順位と効果を判断する。

## 現状と計測

- ビルド時間の計測は `benchmarks/run-cache.mjs`（200 モジュールの whole-build cache の比較）だけです。
- 2026-09-29 の参考値（`--no-cache`、各 1 回、M1 Max）:
  - `examples/hello`: check 0.05 s、実行ファイル `-O0` 0.33 s、`-O3` 0.53 s。C の hello は 0.07 s。
  - 合成 200 モジュール（24,803 行）: check 0.39 s（最大 RSS 237 MB）、実行ファイル `-O0` 1.26 s、`-O3` 2.05 s。
  - 合成 1,000 モジュール（124,003 行）: check 2.12 s（最大 RSS 1.12 GB）、IR 出力 2.58 s（IR 29 MB）、実行ファイル `-O0` 約 6.2 s（うち Clang 3.70 s）、`-O3` 約 10.1 s（うち Clang 7.62 s）。
- 合成コードの入力が定数だったため、`-O3` では計算全体が定数に畳み込まれました。実行性能の比較には使えない生成規則です。
- Go と Zig は計測機に未導入です。

## 目標と指標

- 指標: 初回ビルド（キャッシュなし）、変更なしの再ビルド、1 ファイルの本体だけを変えた再ビルド、1 ファイルの公開シグネチャを変えた再ビルドの wall time。デバッグとリリースを分ける。
- 段階別時間（PX01 の段階別出力）、コンパイラの最大 RSS、成果物サイズ。
- 目標の記録: デバッグビルドの時間を同規模の Go と比較し、差を毎回記録する（合否は判定しない）。

## 施策

- `benchmarks/run-build.mjs`（新規）: 合成プロジェクトの生成器と計測。
  - 生成規則: モジュール数・関数数・関数の形（ループ、match、レコード、union、ジェネリック関数、関数値、文字列）を指定できる。入力は実行時の引数から読み、定数畳み込みで消えないようにする。
  - 同じ構造の Go・Zig・Rust・C/C++ のプロジェクトを生成し、各ツールチェーンがあれば同じ条件でビルドする（Go: `go build`、Zig: `zig build-exe -O Debug／ReleaseFast`、Rust: `cargo build`／`--release`、C/C++: 並列 make）。
  - 実プロジェクト: `examples/` と標準ライブラリを含む全体、ドキュメントのサンプル。
- 並列度（CPU 数）、ツールの版、キャッシュの状態を JSON に記録する。

## 意味・安全性の保持

- 生成したプロジェクトは一時ディレクトリに置き、リポジトリの内容を変えない。
- 計測のための特別なコンパイラの経路を作らない（通常の CLI だけを使う）。

## 検証

- `--quick` で小さな規模の生成・ビルド・実行結果の一致を CI で確認する（時間の閾値なし）。
- 生成したプログラムの実行結果を、各言語の実装間で照合する。

## 受け入れ条件

- [ ] 規模ごとの Tsuzuri のビルド時間・段階別時間・コンパイラの最大 RSS が記録されている。
- [ ] 同じ構造の Go・Rust・C/C++（可能なら Zig）とのビルド時間の比較が記録されている。

## リスク

- 言語ごとに「同じ構造」の意味が異なる（Go のパッケージ、Rust のクレート分割）。分割の粒度を複数用意し、条件を表に明記する。
- ファイルシステムのキャッシュの影響。初回と 2 回目を分けて記録する。

## 対象外

- 分散ビルド、リモートキャッシュの比較。

## 未決事項

- **Rust の分割単位**: 既定案は 1 クレートと、モジュール数に応じた複数クレートの両方を測る。
