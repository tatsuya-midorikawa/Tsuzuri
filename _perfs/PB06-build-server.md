## 目的

コンパイラの状態（標準ライブラリの解析結果、変更されていないモジュールの解析結果、生成物）をメモリに保持し、ファイルを保存してから結果が出るまでを 100 ms 級にする。
エディター（LSP）・ビルド・テスト・REPL（G13）が同じ状態を共有し、同じ解析を繰り返さないようにする。

## 現状と計測

- `build`／`run`／`test`／`check` の各実行は、埋め込みの標準ライブラリを含む全ソースを毎回解析します。hello の `check` でも 0.05 s かかります（2026-09-29）。
- G11 の whole-build cache は解析と IR 生成の後に照合するため、ヒットしても解析の時間は残ります（docs/benchmarks.md）。
- LSP（G07）は変更のたびに全体を検査し、増分の状態を持ちません。
- モジュール単位の解析キャッシュは G17 Phase 2 で計画しています。

## 目標と指標

- 目標: 1 ファイルの本体を変えた後の `check` を 100 ms 以下、`build -O0` を PB05 と合わせて 200 ms 以下にする（124K 行の規模、専用機）。
- 指標: 変更から結果までの時間、サーバーの常駐メモリ。

## 施策

- `tsuzuri build --watch`: ファイルの変更を監視し、変更されたモジュールと、そのシグネチャに依存するモジュールだけを再検査して再ビルドする。
- 常駐サーバー: 利用者ごとの専用ディレクトリのソケット（Unix domain socket／Windows の named pipe）で CLI の要求を受け、状態を共有する。LSP も同じサーバーを使える構成にする。
- 状態の無効化: ソース・manifest・コンパイラの版・環境変数・ツールの変更で該当する状態を捨てる（G11 と同じ入力の規則）。

## 意味・安全性の保持

- 結果（診断・IR・成果物）は、常駐の有無によらずバイト単位で同じにする。定期的に全体を検査して一致を確認するモードを用意する。
- ソケットは利用者本人だけが接続できる権限で作り、他の利用者やネットワークからの接続を受け付けない。要求で指定されたパスは既存の出力保護の規則で検査する。
- メモリの上限を設け、超えたら古い状態を捨てる。

## 検証

- 変更の連続（本体の変更、シグネチャの変更、ファイルの追加・削除・名前の変更）の後の結果が、毎回の全体ビルドと同じであること。
- 同時の要求、サーバーの異常終了と再起動、権限のない接続の拒否のテスト。
- 変更から結果までの時間と常駐メモリの記録。

## 受け入れ条件

- [ ] watch モードと常駐サーバーが、全体ビルドと同じ結果を返す。
- [ ] 変更後の再ビルド時間を実測し、記録している。
- [ ] ソケットの権限と入力の検査のテストがある。

## リスク

- 状態の無効化の誤りは、古い結果を返す不具合になる。無効化の入力を G11 と共有し、一致の検査モードで確認する。

## 対象外

- 複数の利用者で共有するビルドサーバー、リモートのビルド。

## 未決事項

- **既定の起動方法**: 既定案はサーバーを明示的に起動する方式とし、CLI が自動で常駐プロセスを起動することはしない。
