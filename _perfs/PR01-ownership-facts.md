## 目的

C/C++ のコンパイラは、ポインターの別名関係が分からないため多くの最適化をあきらめます（`restrict` を書かない限り）。
Tsuzuri は所有権・借用・不変性により、共有参照の参照先は変更されず、排他参照は他から参照されないことを型検査で保証しています。
この保証を LLVM の属性とメタデータとして伝え、ループの不変式の移動、ベクトル化、冗長な読み込みの除去を C より積極的に行えるようにする。
これは「C/C++ を上回る」ための中心的な施策です。

## 現状と計測

- 2026-09-29 の確認では、生成 IR の内部関数には `nounwind` だけが付き、`noalias`・`readonly`・`nocapture`・`dereferenceable`・`noundef`・関数の `memory(...)` 属性、
  load の `!range`・`!nonnull`・`!tbaa`、スタック領域の `llvm.lifetime.*` はいずれも出力していません（`src/llvm*.rs` の検索で 0 件）。
- `docs/architecture.md`「性能設計の原則」は「既存の所有権・借用・不変性から別名関係や独立性を証明できる場合だけ最適化し、根拠のない `noalias` 等を付けません」としています。
  証明できる事実の付与は未着手です。
- 現在の多くの計算カーネルは C と同等ですが（相対性能 0.99 以上が 25 種目）、別名関係で差が出る種目（参照を受け取る関数内のループ、複数の配列の同時走査）は計測していません。

## 目標と指標

- 別名関係で最適化が変わる種目（例: `ref [f64]` 二つと `ref mut` の作業領域を受け取るループ、参照経由の繰り返し読み込み）を PX02 に追加し、C（`restrict` なし／あり）・Rust と比較する。
- 目標: `restrict` なしの C より速く、`restrict` ありの C・Rust と同等以上。付与の前後で、既存の全種目が遅くならないこと。

## 施策

### Phase 1: 引数と戻り値の属性（証明が単純なもの）

- 共有参照の引数 `ref T`: 参照先は呼び出し中に変更されないため `readonly`、`noalias`（LLVM の意味では書き込みがなければ他の読み取り専用ポインターとの別名を許す）、
  `dereferenceable(<型のサイズ>)`（null にならない値型）、`align`。返さない・保存しない場合は `nocapture`（`captures(none)`）。
- 排他参照 `ref mut T`: 呼び出し中は他の経路から触れられないため `noalias`、`dereferenceable`、`align`。
- 配列・スライスの記述子（`{ ptr, i64 }`）は分解された後のポインターに対し、長さ 0 のとき null になり得るため `dereferenceable_or_null` は使わず、要素の読み込みに範囲の事実を付ける（Phase 2）。
- すべての値引数・戻り値に `noundef`（未初期化の値を作らない）。

### Phase 2: 読み込みと関数の性質

- 配列・文字列・リストの長さの読み込みに `!range !{i64 0, i64 <上限>}`、所有バッファのポインターの読み込みに `!nonnull`（長さが正のときだけ）。
- 関数の `memory(...)` 属性: 本体が extern・IO・Debug・確保・解放・Task を含まない関数は `memory(argmem: read)` などを付け、呼び出しの共通部分式の除去とループ外への移動を可能にする。
- スタック上のリテラル領域と一時領域に `llvm.lifetime.start/end` を付け、重ならない領域を LLVM が共有できるようにする（PM09 と共有）。

### Phase 3: 型に基づく別名情報

- 型の異なる要素（`[i64]` と `[f64]`）の読み書きに TBAA を付ける。ランタイム（`string.ll` など）のバイト単位のアクセスは「すべてと別名になり得る」型にする。

## 意味・安全性の保持

- 付与する事実は、型検査と所有権検査が保証する性質に限る。証明できない場合（関数値の引数、extern、E05 の借用入力、ホストが渡すポインター）は付けない。
- 公開 ABI の wrapper（`tz_*`）では、ホストが契約を守らない場合に未定義動作になる事実を付けない（ホストの入力は検査済みの範囲だけ）。
- 誤った `noalias` は誤った計算結果になる。付与の規則を `docs/architecture.md` の不変条件に列挙し、各規則にテストを付ける。

## 検証

- IR の検査: 各規則が期待どおりの属性を出すこと、証明できない場合に出さないこと（`tests/call_specialization.rs` などの Rust テスト）。
- 全 E2E を native/WASM × `-O0`/`-O3` で実行し、結果・トラップ・確保追跡が変わらないこと。ASan/UBSan で検査する。
- 別名の種目で生成アセンブリ（ベクトル化・ループ外への移動）を確認し、速度を記録する。

## リスク

- `noalias` の付与は LLVM の最適化の誤用で誤計算を招く。A09 の借用フィールド・region、C03 のスライス、関数値の捕捉など、別名の経路を網羅的に洗い出す。
- `memory(...)` の誤りは、副作用のある呼び出しを消す。確保・解放を副作用として扱う。

## 対象外

- 利用者が書く `restrict` 相当の注釈、ホスト側のポインターに対する推測。

## 未決事項
