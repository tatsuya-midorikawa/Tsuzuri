## 目的

`string`（UTF-16 のコード単位列）の意味を変えずに、全コード単位が 0xFF 以下の文字列を 1 単位 1 byte で保存し、英数字中心のテキストのメモリ量をほぼ半分にする。
JVM の Compact Strings や V8 の one-byte string と同じ方式で、比較・検索・変換の速度も上げる。

## 現状と計測

- `string` は「ECMA-262 の String 値モデルに従う、所有する不変の UTF-16 コード単位列」で、`%tz.string = { ptr, i64 }`（ポインターとコード単位数）です（docs/language.md 型とメモリ）。1 単位は常に 2 bytes です。
- `utf8string` は妥当な UTF-8 のバイト列で、ASCII は 1 byte です。
- 2026-09-26 の `cpp/utf16_compare` の相対性能は 0.497 で、最速は JavaScript でした。V8 は Latin-1 の範囲の文字列を 1 byte で保存します。
- 公開 ABI の `ref string` は `const uint16_t *` と長さ、結果の `string` は UTF-16 の所有バッファです（E05）。

## 目標と指標

- 目標: ASCII 中心のテキストを扱う種目（単語の出現数、CSV、JSON）で、文字列のメモリ量を約半分にし、比較・検索を JavaScript と同等以上にする。
- 指標: 文字列のメモリ量、最大 RSS、文字列の種目の時間。非 Latin-1 のテキストで退行しないこと。

## 施策

- 表現: 記述子に符号化の印（1 byte／2 bytes）を持たせる。候補は長さの最上位 bit（長さは `i64` の正の範囲に収まる）または確保のアラインメントを使ったポインターの下位 bit。
- 生成規則: リテラル・連結・部分文字列・変換の結果は、全単位が 0xFF 以下なら 1 byte 形式にする。混在する連結は 2 bytes 形式へ広げる。
- 全ての文字列操作（索引、長さ、比較、Hash、Display、検索、分割、変換）を両形式に対応させる。索引と長さは UTF-16 のコード単位のまま（1 byte 形式では 1 単位 = 1 byte なので O(1) を保つ）。
- ABI の境界: 借用入力（ホストの UTF-16）は 2 bytes 形式のまま扱う。所有結果をホストへ返すときは UTF-16 へ広げる（確保と変換のコストを文書化する）。E13 の生成バインディングで、ABI の新しい版として 1 byte 形式を渡す選択肢を検討する。

## 意味・安全性の保持

- 観測できる値（コード単位の列、長さ、索引、比較の順序、Hash の canonical な値、Display の出力、孤立サロゲートの保持）を完全に同じにする。
- 公開 ABI の既存の型（`const uint16_t *`）を変えない。

## 検証

- 全文字列テストを両形式の入力（Latin-1 のみ、混在、サロゲート）で実行し、結果を 2 bytes 形式だけの実装と照合する（差分テスト）。
- native/WASM × `-O0`/`-O3`、ASan、確保追跡。
- 文字列の種目のメモリ量と時間を記録する。

## 受け入れ条件

- [ ] 両形式で全ての文字列操作の結果が一致し、既存のテストが通る。
- [ ] ASCII 中心の種目でメモリ量と時間の改善を実測し、非 Latin-1 の入力で退行がない。
- [ ] 内部表現の変更が承認され、docs に記録されている。

## リスク

- 全ての文字列ランタイムに分岐が入る。短い文字列の操作が遅くならないか計測する。
- 変更範囲が広い（ランタイム・Display・Hash・ABI・デバッグ表示）。段階的に導入し、各段で差分テストを行う。

## 対象外

- UTF-8 を既定の文字列にする変更（言語の意味の変更）、rope などの遅延連結の表現。

## 未決事項

- **印の置き場所**: 既定案は長さの最上位 bit。ポインターの下位 bit は静的リテラル・スタック上の領域のアラインメントの保証が必要。
- **承認**: 内部表現の変更として承認を得るまで着手しない。
