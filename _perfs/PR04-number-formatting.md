## 目的

数値の文字列化と解析を、C++ の `std::to_chars`／`from_chars` や .NET と同等以上の速さにする。
JSON・CSV・ログなどのデータ変換（Tsuzuri の主要な用途）で、数値の入出力がボトルネックにならないようにする。

## 現状と計測

- 2026-09-26 の `cpp/format_parse` の相対性能は 0.751（最速は C#、C++ も Tsuzuri より速い）でした。
- 浮動小数点の最短表示は `src/runtime/numeric.c` の `shortest`（多倍長整数による Dragon4）で、f16/f32/f64/f128 に共通です。
- 整数の表示は 2 桁ずつの除算（表を使わない）です。表を使う試作は、Clang 23 の wasm32 `-O0` で不正なコードを生成したため採用していません（2026-09 の記録）。
- 解析は 8 桁ずつの読み取りと多倍長整数による正確な丸めです。f32/f64 の高速経路はありません。
- 表示・解析は native と WASM で同じ結果を返し、ホストの locale・printf・浮動小数点の中間値を使いません（D-11）。

## 目標と指標

- 目標: `format_parse` で C++（`to_chars`／`from_chars`）と C# の最速と同等以上。f32/f64 の表示・解析の 1 回あたりの時間を型別に記録する。
- 結果は現在の実装とビット単位・文字単位で同一であること。

## 施策

- f32/f64 の最短表示に、正しさが証明されたアルゴリズム（Schubfach、Ryū、Dragonbox のいずれか）を実装する。f16/f128/decimal は現在の Dragon4 を使う。
- f32/f64 の解析に、Eisel–Lemire の高速経路を追加し、判定できない入力だけ現在の正確な経路へ戻す（fast_float と同じ構成）。
- 整数の表示: 64-bit 以下は除算回数を減らす方式（2 桁の表、または表を使わない乗算による桁の抽出）を、native/WASM × `-O0`/`-O3` と固定の Clang の版で検証してから採用する。
- 表を使う場合は、表の配置と生成 IR が wasm32 の全最適化レベルで正しくなることを確認する。

## 意味・安全性の保持

- 出力の文字列は D-11 の規則（最短往復、同じ桁数なら近い方、等距離なら偶数）と完全に一致させる。解析の丸めも一度だけの最近接・偶数丸めを保つ。
- 高速経路の採否はビット単位の比較で検証してから決め、既存の経路を代替として残す。

## 検証

- 既存の `tests/display_parse.mjs`（表示 88,063 件、解析・往復 111,282 件など）を全経路で実行する。
- f32 は全 2^32 のビットパターンを専用環境で表示・解析して往復を確認する。f64 は境界値・乱択（1 億件以上）・既知の難しい入力の集合で確認する。
- 型別の 1 回あたりの時間（`tests/display_parse_runtime.c` の F/P プロトコル）と生成コードを記録する。
