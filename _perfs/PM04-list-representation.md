## 目的

`[|T|]`（不変の単方向連結リスト）を、要素ごとのノードではなく連続したバッファで表し、メモリ量を数分の一にし、走査を速くする。
Tsuzuri のリストは一意に所有され共有されないため、構造の共有を前提にした連結ノードでなくても、観測できる意味を保ったまま表現を変えられます。

## 現状と計測

- `%tz.list = { ptr, i64 }`（先頭ノードと長さ）、ノードは `{ ptr 次, T }` で要素ごとに確保します（`new [|...|]` はノードごとにヒープ、束縛したリテラルのノードはスタック）。
- `[|i64|]` の 1 要素は、ノード 16 bytes に確保のオーバーヘッドが加わります。WASM の allocator は 16 bytes のヘッダーと 16 bytes 単位の丸めで、1 要素あたり 32 bytes です。配列 `[i64]` は 8 bytes です。
- `List.cons`（先頭に追加）と `List.tail`（先頭を除く）は O(1)、`values[index]` は O(index + 1)、`.length` は O(1) です（docs/language.md）。
- 2026-09-26 の `control/list_sum`（10000 要素）は Tsuzuri が最速でしたが、メモリ量は計測していません。

## 目標と指標

- 目標: 要素がスカラーのリストで、1 要素あたりのメモリを配列と同程度（8 bytes + 容量の余裕）にする。走査・生成の時間を現状以下にする。
- 指標: リストを多用する種目のメモリ量と時間、確保回数。

## 施策

- 表現: 要素を逆順に格納する伸縮バッファ `{ ptr, 長さ, 容量 }`。先頭要素はバッファの末尾にあり、`cons` は末尾への追加（償却 O(1)）、`tail` は長さを 1 減らして先頭要素を解放する O(1)、索引は O(1) になる。
- 所有権: リストは一意に所有されるため、`cons` と `tail` はバッファをその場で更新できる。Copy のリストの複製はバッファの複製（現在のノードの複製と同じ O(n)）。
- リテラルのスタック配置は、連続した領域として保つ。スタック上のリストへの `cons` は、現在の移送規則と同じくヒープへ移してから行う。
- パターン（先頭と残りの分解）、`List.iter`、構造比較（A11）、Display、Hash、反復 drop を新しい表現に合わせる。

## 意味・安全性の保持

- 要素の評価順序、所有権の移動、解放の順序と一回性、トラップの条件を変えない。
- 観測できる計算量は同じか改善のみ（索引が O(1) になる）。docs の記述を更新する。
