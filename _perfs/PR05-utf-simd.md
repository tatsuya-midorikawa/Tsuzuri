## 目的

UTF-8 と UTF-16 の変換・検証・比較を、simdutf などの SIMD 実装と同等の速さにする。
Tsuzuri の既定の `string` は UTF-16 で、ホストやファイルの UTF-8 との変換が頻繁に起こるため、変換の速度がデータ処理全体の速度を左右します。

## 現状と計測

- 2026-09-26 の相対性能: `cpp/utf8_roundtrip` 0.658（最速は C++）、`cpp/utf16_compare` 0.497（最速は JavaScript）。`utf16_scan` と `utf16_validate` は Tsuzuri が最速でした。
- 一致検査は範囲内の 64-bit 読み出しでまとめ、辞書順は不一致位置の 16-bit の符号なし比較です。UTF 変換は、入出力の長さが等しい（ASCII）ときだけ ASCII の書き込みへ進み、それ以外は 1 文字ずつの復号です（docs/benchmarks.md）。
- ASCII を各位置で先読みする試作は、Unicode が混在する入力を遅くしたため破棄されています。
- 実行時の CPU 選択は同梱の `Array.sum<i64>` だけです（F05）。

## 目標と指標

- 目標: `utf8_roundtrip` で C++ の最速と同等以上、`utf16_compare` で JavaScript と同等以上。
- 入力の種類（ASCII のみ、ラテン文字の混在、CJK、絵文字、不正な列）ごとに時間を記録する。

## 施策

- 128-bit のベクトル（NEON／SSE2、WASM は simd128 指定時）を baseline とする変換・検証のカーネルを C ランタイムに追加する。
  ASCII の連続区間はブロック単位で判定し、非 ASCII の区間はブロック単位の復号（simdutf と同じ種類のアルゴリズム）で処理する。
- AVX2 などの幅の広い命令は、F05／F08 の実行時選択の仕組みで版を切り替える。
- 比較: 一致検査と辞書順を、ベクトルの一致判定と最初の不一致位置の検出で行う。短い文字列では現在のスカラー経路を使う。
- WASM の既定（SIMD なし）では現在の経路を維持し、`--wasm-feature simd128` でだけベクトル版を使う（D-18）。

## 意味・安全性の保持

- 結果（変換後の列、不正な UTF-8 の判定、孤立サロゲートの扱い、比較の順序）は現在の実装とビット単位で同一にする。
- 読み取りは入力の範囲内に限り、ページ境界を越える投機的な読み込みをしない（ASan で検査する）。

## 検証

- 全 Unicode スカラー、全孤立サロゲート、全ての不正な UTF-8 の短い列、長さ 0〜257 の全長と各アラインメントの組み合わせで、スカラー版と結果を照合する。
- native/WASM（SIMD 有無）× `-O0`/`-O3`、ASan/UBSan。
- 入力の種類ごとの時間と、生成アセンブリのベクトル命令を記録する。

## 受け入れ条件
