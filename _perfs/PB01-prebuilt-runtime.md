## 目的

ビルドのたびに同じランタイムを Clang でコンパイルし直す処理をなくし、小さなプログラムのビルドを C のコンパイルと同じ程度の時間にする。
現在の最も大きく、最も解消しやすいビルド時間の無駄です。

## 現状と計測

2026-09-29、`--no-cache`、M1 Max:

- `examples/hello` の実行ファイルのビルドは `-O0` 0.33 s、`-O3` 0.53 s。フロントエンド（IR の出力まで）は 0.02 s、C の hello は 0.07 s です。
- ライブラリとしての IR は 3 KB ですが、実行ファイルでは結果の表示のために数値ランタイム（`numeric.ll`、11,337 行）が IR に連結され、464 KB になります。
  この IR の Clang `-O3` のコンパイルだけで 0.43 s、`-O0` で 0.06 s でした。
- Task を使うプログラムでは、ビルドのたびに `task.c` を Clang でコンパイルします（`-O3` で 0.08 s）。`cpu.c`・`io.c` も同じ方式です。
- `emit_target` は生成した IR の文字列に特定のシンボル（`@tz_soft_` など）が現れるかを検索し、該当するランタイムの IR 全体を連結します（`src/llvm.rs`）。
- G11 の whole-build cache は同じ入力の再ビルドを省きますが、入力が変わればランタイムも再コンパイルします。

## 目標と指標

- 目標: hello の実行ファイルのビルドを `-O0`／`-O3` とも 0.1 s 以下（C の hello と同程度）にする。
- 指標: PX03 の段階別時間（外部ツールの時間）、小さな例の全体の時間。

## 施策

### Phase 1: ランタイムの事前コンパイルとキャッシュ

- ランタイム（`numeric.ll`、`math.ll`、文字列・ヒープ・表示の IR、`task.c`、`cpu.c`、`io.c`）を、target・最適化レベル・CPU 指定・WASM の機能の組ごとに一度だけ object にコンパイルし、キャッシュに保存する。
- キャッシュの key はコンパイラの SHA-256、Clang の digest と版、ランタイムのソース、コンパイルの指定（G11 と同じ規則）。保存・検証・破損時の扱いは G11 の方式を共有する。
- 配布物（G14）には主要な組の事前ビルド済み object を含められるようにする。

### Phase 2: 必要な関数だけのリンク

- ランタイムの object を関数ごとの section（`-ffunction-sections`）で作り、リンカーの未使用コード除去で使う関数だけを残す。
- 整数・bool の表示が浮動小数点・decimal の処理を参照しないよう、表示の関数を型ごとに分ける（PM08 と共有）。

### Phase 3: 生成 IR の検索の置き換え

- 使うランタイムの判断を、IR の文字列の検索ではなく、IR 生成時に記録する使用シンボルの集合で行う（PB02 の IR 生成の改善と共有）。

## 意味・安全性の保持

- ランタイムの内容・最適化レベルは現在と同じにする。インライン展開の機会が減る小さな関数（文字列の比較・確保など）は、計測して IR に残すかを決める。
- 生成物は決定的で、キャッシュの有無で内容が変わらない。
- キャッシュの保存場所は G11 と同じ保護（専用のマーカー、原子的な公開、破損の検出）を使う。

## 検証

- 事前コンパイルの有無で、全 E2E（native/WASM × `-O0`/`-O3`、ASan）の結果と実行ファイルの動作が同じこと。
- キャッシュの無効化（コンパイラ・Clang・ランタイムの変更）、破損、同時ビルドのテスト（`tests/cache.mjs` と同じ形式）。
- `scripts/check-runtime-includes.sh` の検査を新しい構成に合わせる。
- 小さな例の段階別時間を記録する。

## 受け入れ条件

- [ ] 同じ組のランタイムが二回目以降のビルドで再コンパイルされない。
- [ ] hello のビルド時間の改善を実測し、記録している。
- [ ] 実行結果・トラップ・確保追跡が変わらない。

## リスク

- ランタイムを別の object にすると、LLVM が利用者のコードとランタイムをまたいで最適化できなくなる。実行速度の退行を PX01 で確認し、必要な関数は IR のまま残す。
- macOS の relocatable link の既知の注意点（`-keep_private_externs` による task runtime の統合）を、新しいリンク構成でも保つ。

## 対象外

- 利用者コードの関数単位のキャッシュ（PB07）、フロントエンドの高速化（PB02）。

## 未決事項

- **既定のキャッシュ場所**: 既定案は G11 の cache ディレクトリの下に置き、`--no-cache` ではランタイムのキャッシュも使わない。
